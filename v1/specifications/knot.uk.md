# Knot v1

Контракт `Knot` підтримує геометричні представлення 2D і 3D, сіткові діаграми, мозаїчні діаграми, коди планарних діаграм, коди Даукера–Тістлетвейта, конструкції, іменовані стани, алгоритми та спільні ресурси. `RawKnot` — серіалізовані дані; підготовлений `Knot` надає методи під час виконання. Інші формати представлень, анімація, властивості, відношення та класифікації потребують окремих контрактів; нетипізовані поля для них не приймаються. Див. [відкриті проєктні питання](../../design/knot-draft.uk.md).

## Термінологія

Описові поняття подаються українською. Коли йдеться про конкретний об’єкт даних, явно вказується `Knot`; слово «документ» використовується для серіалізованих документів або документації, а не як безумовний замінник назви типу. У відповідних місцях обох мовних версій використовується однакове кодове оформлення. Заголовки подаються звичайним текстом, зокрема технічні назви. Точні назви типів, функцій, полів і значення кодів в основному тексті оформлюються як код; назви продуктів і джерел (KnotInfo, Gridlink) зберігаються. X/O — назва системи позначень; `xo` та `vertex-pairs` — точні значення поля `encoding`. Назва файла або типу не замінює описового поняття в переліку можливостей.

## Документи та ідентичність

`Knot` вимагає `schema: "Knot"`, `schemaVersion: 1`, `id` і `subject: {id}`. Необов’язкові колекції: `sources`, `contributions`, `catalogs`, `representationTypes`, `objectTypes`, `algorithmPurposes`, `tileSets`, `conventions`, `constructions`, `representations`, `algorithms`, `dependencies`. Необов’язкове `$schema`, якщо задане, має ідентифікувати відповідну опубліковану JSON Schema. `namespaces` оголошує префікси компактних URI. Відомі об’єкти закриті: невідомі поля є помилками навіть при переданому `strict: false`.

`knot.id` ідентифікує документ, `subject.id` — предмет опису. У початковому профілі ID можуть бути локальними рядками або абсолютними/компактними URI. Незалежні документи не об’єднуються за ідентичністю предмета опису. `subject.names` і `subject.descriptions` містять записи `{language,value}` для локалізованих назв і описів предмета; обидва поля необов’язкові, до 128 записів кожне. `language` і `value` — непорожні рядки; мовні теги варто задавати за BCP 47 (`en`, `uk` тощо). Ці масиви не задають мову переглядача й не визначають автоматичного вибору резервної мови. `subject.identifiers` містить записи `{catalog,value}`. Каталог є системою позначень, а не колекцією всіх її записів. Правила перевіряють форму позначення, а не істинність авторської ідентифікації.

Відсутні та порожні колекції не встановлюють повноти знань. Knot лише з описом предмета валідний; для 3D-показу потрібне придатне представлення.

## Простори імен та посилання

Глобальні ідентифікатори — абсолютні URI `http`, `https`, `urn` або оголошені `prefix:suffix`. Розгортання з’єднує URI простору й суфікс. Префікси `http`, `https`, `urn` зарезервовані без урахування регістру. Неоголошений префікс є помилкою. Розгорнуті URI порівнюються точно; завантаження, зміни регістру чи канонізації URL немає. Вбудований простір: `https://yuriyapostol.github.io/knot-engine/v1/`.

Префікси діють також у нашому полі `dataSchema.ref`, у `data.convention` стандартних DT/PD-представлень і в `data.tileSet` стандартного мозаїчного представлення. Тип представлення розгортається першим і визначає, які поля даних можна розгортати. Довільні дані невідомих типів, URL джерел і вміст `dataSchema.inline` не переписуються. Кожен документ або реєстр має власні `namespaces`; при перенесенні компактного фрагмента в інший документ потрібно перенести і відповідні оголошення або попередньо розгорнути URI.

JSON Schema не розгортає значення даних за нашими `namespaces`. Самостійні схеми DT/PD/мозаїк і прямі валідатори приймають підтримувану стандартну коротку назву або її канонічний URI. Оголошені компактні URI потребують контексту документа й розгортаються валідаторами `Knot` та `RawRepresentationDocument`. Канонічні `$id` схем залишаються повними URI.

Локальні посилання мають форму `{id: string}`, зовнішні ресурсні — `{ref: URI}`. Форми взаємовиключні. Локальні посилання розв’язуються тільки у визначеній області; глобальний ресурс можна включити до об’єкта `Knot` і адресувати через `{ref}`. `$id`/`$ref` JSON Schema та редакторський `$schema` зберігають стандартну семантику URI без компактних префіксів.

Незмінні стандартні визначення з `STANDARD_RESOURCES` завжди доступні. Вузли лише зі стандартними типами не потребують `representationTypes`, `objectTypes`, `algorithmPurposes`, `tileSets`, `conventions` або явного реєстру. Зовнішні визначення можна вкладати або явно передавати через `options.registries`; зовнішні посилання ніколи не завантажуються. Зарезервовані стандартні ідентичності не можна перевизначити іншим видом або контрактом. Різні визначення з однаковим глобальним ID спричиняють помилку; однакові JSON-об’єкти без урахування порядку ключів можна дедуплікувати. Порядок масивів значущий. Дані невідомих представлень зберігаються без переписування довільних полів.

## Стандартні назви та ідентичності ресурсів

Наведені зарезервовані короткі назви з урахуванням регістру є частиною контракту v1 як усередині пакета, так і поза ним:

| Поле | Стандартні назви | Суфікс канонічного URI |
| --- | --- | --- |
| `Representation.type` і запити представлень | `2d`, `3d`, `grid-diagram`, `mosaic-diagram`, `pd-code`, `dt-code` | `representation-types/<name>` |
| `ConstructionObject.type` | `rope`, `support`, `carabiner` | `object-types/<name>` |
| `Algorithm.purpose` | `tying`, `untying`, `transformation`, `adjustment` | `algorithm-purposes/<name>` |
| `Representation.data.tileSet` для мозаїк | `lomonaco-kauffman-11` | `tile-sets/<name>` |
| `Representation.data.convention` для PD/DT | `pd-ccw-under-first`, `dt-signed-even` | `conventions/<name>` |

Суфікси відраховуються від `https://yuriyapostol.github.io/knot-engine/v1/`. Коротка назва, її канонічний URI та оголошений компактний URI позначають той самий ресурс. Короткі назви обмежені видом ресурсу відповідного поля; довільні короткі назви, ID документів і локальні посилання не стають скороченнями ресурсів. Простори імен не можуть замінити зарезервовані написання. Власні типи й призначення використовують абсолютні або оголошені компактні URI.

Нормалізація та вибір порівнюють канонічні URI. Підготовлені об’єкти й `toRaw()` зберігають авторські короткі назви; виділення/композиція повертають нормалізовані дані. `knot.select()` створює самодостатній фрагмент із канонічними ідентичностями й потрібними визначеннями стандартних/власних типів та призначень. Сам URI не робить експорт самодостатнім. Повторення однакових визначень допускається; зміна стандартного контракту або виду ресурсу відхиляється. Локалізовані назви можна перевизначати без зміни контракту.

`resolveResourceURI(value, kind, namespaces?)` розв’язує ці назви або URI; загальна `expandURI()` надалі працює лише з URI. Самостійні схеми й валідатори DT/PD/мозаїк приймають стандартні короткі назви або канонічні URI конвенцій/наборів плиток. Валідація документів додатково розгортає оголошені префікси перед семантичними перевірками. JSON Schema не розв’язує довільні простори імен; гілки документів із короткими типами приймають непорожні рядки конвенцій/наборів плиток, а ядро перевіряє їхню канонічну ідентичність.

Набори плиток і конвенції є ресурсами видів `tile-set` і `convention`. Їхні визначення вимагають `id`, `name`, `description`, `specification` і можуть містити локалізовані `names` та `descriptions`; `dataSchema` не задається. Власні визначення можна вкладати в `tileSets`/`conventions` або передавати реєстром. Стандартні визначення доступні автоматично й включаються до самодостатнього експорту. Наявність стороннього визначення не розширює підтримувану семантику: чинний профіль мозаїк приймає лише набір Ломонако—Кауфмана, а PD і DT — лише відповідну стандартну конвенцію. Дані невідомих типів не переписуються за самою назвою поля.

## Конструкції та алгоритми

Конструкція вимагає `id` і непорожній `objects`; необов’язкові поля — `name`, `description`, `states`. Предмети вимагають локальний `id` і `type` у формі стандартної короткої назви або URI. ID унікальні в межах конструкції; однакові локальні ID в різних конструкціях означають різні предмети. Іменовані стани вимагають `id`, можуть містити `name` та `description`. ID станів локальні до конструкції.

Вбудований тип мотузки має `topology: open | closed` і `ends`. Відкрита мотузка має два кінці з різними ID, замкнена — жодного. Необов’язкові `length` і `diameter` — додатні скінченні метри. Профілі опори й карабіна поки містять тільки `id` і `type`; їхні криві не визначають стандартизовану форму спорядження. Додаткові типи потребують визначення та схеми й залишаються семантично неперевіреними без підтримуваного валідатора.

Відсутній `target` представлення означає предмет опису документа. Явні форми: `{kind:"subject"}`, `{kind:"construction",construction:Reference}`, `{kind:"state"|"object",construction:Reference,id:string}`. Стани й предмети шукаються в указаній конструкції.

Алгоритм вимагає `id` і непорожній `steps`; необов’язкові локалізовані масиви `names`, `descriptions` записів `{language,value}` та `construction` задають контекст. Крок має унікальний локальний `id`, необов’язкові `descriptions` (масив записів `{language,value}`) і `representations` (локальні посилання `{id}` у цьому профілі). Крок може не мати ілюстрацій або мати декілька. Алгоритм не вимагає однакової кількості точок, інтерполяції чи часу анімації. Стан може використовуватися кількома алгоритмами й представленнями.

Представлення можуть містити необов’язкові `names` і `descriptions` у форматі `{language,value}`, аналогічному `subject`. Алгоритми (`algorithms`) можуть містити необов’язкові локалізовані `names` і `descriptions` у форматі `{language,value}`. Кроки алгоритму можуть містити `names` і `descriptions` у тому самому форматі; описи можуть пояснювати крок або описувати дії для виконання. Ці поля не визначають мову інтерфейсу або резервний переклад.


`RawAlgorithm.base?: Reference` вказує базове геометричне представлення, зокрема фінальне. `RawStep.data?` описує незалежне перевизначення бази: `remove?: string[]` видаляє наявні елементи, `replace?: Element[]` замінює цілі наявні елементи, `add?: Element[]` додає нові елементи. Необов'язкове `crossings?: Crossing[]` повністю замінює перелік перетинів для 2D (порожній масив очищує його). Відсутні операції означають відсутність змін. Кроки не застосовуються один до одного; тип і система координат бази не змінюються. `Step.data` вимагає `Algorithm.base`; `Step.representations` зберігається. `Construction.states` також зберігається.

Текст кроків, раніше записаний у `instructions`, потрібно перенести до `descriptions`; поле `instructions` більше не приймається. Підготовлені кроки надають `getDescription()` замість `getInstructions()`.

Колишня колекція `procedures` тепер має назву `algorithms`; старе поле більше не приймається. Замініть `RawProcedure`/`Procedure` на `RawAlgorithm`/`Algorithm`, `getProcedure`/`addProcedure`/`removeProcedure` на `getAlgorithm`/`addAlgorithm`/`removeAlgorithm`, а параметр `select()` — на `algorithms`. Семантика базового представлення та незалежних перевизначень кроків зберігається. Алгоритми можуть описувати зав’язування, розв’язування, перетворення чи регулювання.

### Умови, повтори та призначення

`RawAlgorithm.purpose?` посилається на ресурс `algorithm-purpose`. Стандартні короткі назви класифікують алгоритм: `tying` (зав’язування), `untying` (розв’язування), `transformation` (перетворення одного вузла на інший) або `adjustment` (укладання, підтягування чи регулювання наявного вузла). Власні призначення використовують абсолютні URI або оголошені компактні URI та потребують визначення в `algorithmPurposes` або явному реєстрі. Відсутні визначення призначень роблять валідацію неповною; неправильний вид ресурсу є помилкою. Визначення призначення вимагає `id`, `name`, `description`, `specification` і може містити локалізовані `names` та `descriptions`; воно не має `dataSchema`. Відсутнє поле залишає призначення невизначеним. Призначення не задає початкового чи кінцевого стану, не змінює `base` та не встановлює ідентичності іншого вузла.

`RawStep.condition?` — непорожній локалізований масив записів `{language,value}` (1–128 записів із непорожніми рядками), що описує умову виконання кроку. Записи є перекладами однієї умови. Людина оцінює її один раз перед усім кроком; хибна умова пропускає крок цілком, включно з усіма повторами. Без умови крок безумовний. Умови є описовим текстом, а не виконуваними виразами; рушій їх не обчислює й автоматично не вибирає переходи. Підготовлені кроки надають `condition` як `LocalizedTexts` і `getCondition(language?)` з мовою та резервним вибором свого вузла, без перевизначень назв/описів.

`RawStep.repeat?` задає **загальну кількість виконань**, а не додаткові повтори після першого:

| Форма | Значення |
| --- | --- |
| `{count: 3}` | Рівно три виконання |
| `{min: 2, max: 4}` | Від двох до чотирьох виконань |
| `{min: 2}` | Щонайменше два виконання, без верхньої межі |
| `{max: 4}` | Від одного до чотирьох виконань |

Усі задані кількості мають бути додатними цілими числами. Потрібне щонайменше одне з полів `count`, `min`, `max`; `count` несумісне як із `min`, так і з `max`. Валідатор ядра додатково перевіряє `min <= max`, якщо задано обидва поля; стандартна JSON Schema перевіряє структуру полів, але не може порівняти ці сусідні значення. Відсутнє `min` означає 1; відсутнє `max` — відсутність верхньої межі. Без `repeat` крок виконується один раз. Якщо умова хибна, допускається нуль виконань незалежно від мінімальної кількості повторів. У межах діапазону кількість виконань вибирає людина. Повторна перевірка умов між виконаннями та автоматичне розгалуження поза цим контрактом.

Ці поля описують дії людини. Вони не накопичують патчі геометрії, не генерують проміжні представлення й не змінюють незалежного застосування `Step.data` до бази алгоритму. Див. [приклад зав’язування та розв’язування зі спільними представленнями](../examples/knots/algorithm.json).

## Представлення

Представлення вимагає `id`, `type` (стандартна коротка назва або URI) і `data`; необов’язкові поля — `target`, `names`, `descriptions`, `sources`, `contributions`. ID унікальні в об’єкті `Knot`. Визначення типу вимагає `id`, `name`, `description`, `dataSchema`, `specification`; необов’язкове `viewSpace` — `none` (типово), `plane` або `space`. Визначення типів предметів мають ті самі поля, крім `viewSpace`.

`dataSchema` — `{ref: абсолютний-або-компактний-URI-схеми}` або `{inline: об’єкт-JSON-Schema}` з явним діалектом `$schema`. Зовнішні схеми передаються через `options.schemas`; мережевого resolver немає. Поточний рушій користувацьких схем підтримує draft 2020-12. Схема не доводить доменну семантику. Невідомий тип може пройти структурну перевірку, залишившись у `uncheckedTypes`; його не можна відрендерити або експортувати як перевірений самодостатній фрагмент.

### Геометричні представлення 2D і 3D

Типи представлень `representation-types/2d` та `representation-types/3d` використовують `data.elements` — масив елементів з унікальними `id`, дискримінатором `type` та необов'язковим `object`, що посилається на об'єкт конструкції. Усі координати задаються в системі координат представлення, без локальних трансформацій.

Для `2d` підтримується `curve` із `closed` і однією з форм: `interpolation` та `points: [number, number][]` або `start` та явні `segments` (див. нижче). Для `3d` підтримуються обидві форми `curve` із тривимірними точками та `mesh` із `vertices: [number,number,number][]` і трикутними `faces: [number,number,number][]` (індекси від нуля). `3d.coordinateSystem` є правобічною з віссю Y вгору; `2d.coordinateSystem` використовує вісь X праворуч, Y вгору та `scale` за тими самими правилами.

Необов'язкове `2d.data.crossings` задає порядок проходжень кривих через перетини. Кожен перетин має рівно два записи з однаковим `id`; кожен запис містить `element` і рівно одне з `underElement` (інший елемент нижче поточного) або `overElement` (інший елемент вище поточного). Підпослідовність записів для кожного `element` упорядкована за проходженням від першої точки кривої (`start` для сегментної форми). Самоперетин описують два проходження того самого елемента з протилежним порядком накладання. Координати перетинів не зберігаються, а обчислюються з геометрії. Дотики та збіжні ділянки не підтримуються.





`data` містить `coordinateSystem` і непорожній `elements`. Початковий профіль — права система з Y угору: `{handedness:"right",upAxis:"y",scale}`. Масштаб: `{kind:"relative"}` або `{kind:"physical",metersPerUnit: додатне-число}`. Імпорт не виводить фізичний масштаб і не пересуває точки приховано.

Інтерпольована крива вимагає `id`, `closed`, `interpolation`, `points`; необов’язкове `object` ідентифікує предмет цільової конструкції. Без посилання на предмет крива може описувати предмет опису без фізичної конструкції. Точки — скінченні XY-пари у 2D або XYZ-трійки у 3D, щонайменше дві для відкритої кривої та три для замкненої. Послідовні дублікати й повторена кінцева точка замкненої кривої відхиляються за точною рівністю координат. Геометричне замикання відокремлене від топології мотузки.

Інтерполяція має одну з форм:

- `{type:"polyline"}`;
- `{type:"catmull-rom",parameterization:"uniform",tension: число-в-[0,1]}`;
- `{type:"catmull-rom",parameterization:"centripetal"}`;
- `{type:"catmull-rom",parameterization:"chordal"}`.

Сегментна 2D- або 3D-крива натомість вимагає `id`, `type:"curve"`, `closed`, `start: [x,y]` (2D) або `start: [x,y,z]` (3D) і непорожній масив `segments`. Необов’язкове `object` має те саме значення. Форми взаємовиключні: `points`/`interpolation` не можуть співіснувати зі `start`/`segments`. Кожен сегмент починається в кінці попереднього, для першого — у `start`, і має одну з форм:

- `{type:"line",end:[x,y]}`;
- `{type:"quadratic",control:[x,y],end:[x,y]}`;
- `{type:"cubic",control1:[x,y],control2:[x,y],end:[x,y]}`.

Усі координати — абсолютні скінченні XY-пари у 2D або XYZ-трійки у 3D в системі координат представлення. Поля сегментів однакові для обох розмірностей. Сегменти можна довільно змішувати; гладкість задають контрольні точки, автоматичного згладжування немає. `closed:true` має семантику SVG `Z`: з’єднує останню кінцеву точку зі `start` прямим сегментом, якщо вони різні. Для замикання сегментом Безьє його кінець явно задають у `start`. Збіги контрольних точок, повторні кінцеві точки й сегменти нульової довжини дозволені; правила дублікатів і мінімальної кількості точок інтерпольованої форми тут не діють. Один кубічний сегмент може утворити замкнену петлю. Повністю вироджені криві можуть пройти структурну перевірку, але переглядач відхиляє геометрію без ділянок, придатних для відображення.

Сегментна крива допускає щонайбільше 4096 сегментів. Бюджети 65536 точок геометрії/документа враховують її початок, кожну кінцеву й усі контрольні точки. Сегментні криві підтримуються в операціях `add`/`replace` 2D- і 3D-алгоритмів; координати початку, кінців і контрольних точок мають відповідати розмірності бази. Наявні інтерпольовані дані не потребують міграції. У TypeScript `Curve2D` є об’єднанням `InterpolatedCurve2D` і `SegmentedCurve2D`, а `Curve3D` — об’єднанням `InterpolatedCurve3D` і `SegmentedCurve3D`; перед доступом до полів окремої форми звузьте тип через `'segments' in curve`. Див. [перетворення SVG path](functions.uk.md#перетворення-svg-path) і [приклад Безьє у 2D](../examples/knots/bezier-2d.json) і [приклад Безьє у 3D](../examples/knots/bezier-3d.json).

Засіб візуалізації працює в координатах даних. Фізичний діаметр мотузки перетворюється на радіус `diameter / (2 * metersPerUnit)`. Інакше радіус показу дорівнює 0.006 найбільшого розмаху контрольних точок і супроводжується попередженням; це не фізичний вимір. Засіб візуалізації відхиляє компоненти координат/камери поза ±1,000,000 та недодатні або більші за 1,000,000 радіуси. Це обмеження рендерингу, відокремлені від доменної валідації. Трубчаста сітка наближує криву й не доводить топології вузла або відсутності зіткнень.


У 2D-перетинах поле `type` може мати значення `classical` (типово, якщо пропущене), `unknown` або `virtual`. Класичні проходження використовують `underElement`/`overElement`, інші — `otherElement`. Парні проходження мають однаковий ідентифікатор та тип перетину. Див. [схему геометрії 2D](../schema/2d.schema.json).

### Представлення зображення

Вбудований тип `image` зберігає `mimeType` і `src`, не кодує топологію. Див. [контракт зображення](image.uk.md).

### Сіткові діаграми (xo, vertex-pairs)

Тип: `https://yuriyapostol.github.io/knot-engine/v1/representation-types/grid-diagram`.

`data` має форму `{encoding:"xo",size,x,o}`. Розмір — ціле число від 2 до 512; обидва масиви є перестановками індексів рядків `0..size-1`, індексованими за стовпцем. X та O у кожному стовпці різні. Нульовий рядок нижній, стовпці зростають праворуч. Горизонтальні дуги йдуть O→X; вертикальні X→O і проходять над горизонтальними. Профіль підтримує кілька компонентів і не визначає тотожності вузла. Реалізовано дані, валідацію та вбудований SVG-переглядач сіткових діаграм. Альтернативний профіль `{encoding:"vertex-pairs",size,vertices}` зберігає неорієнтовані різні пари `[column,row]` з індексами від 0, рівно по дві на рядок і стовпець.

Деталі лічильників, координат і сумісності з KnotInfo — у [специфікації сіткових діаграм](grid-diagram.uk.md).

### Мозаїчні діаграми

Профіль визначено у [специфікації мозаїк](mosaic-diagram.uk.md). Реалізовані типи, JSON Schema, стандартний ресурс та семантична перевірка `validateMosaicDiagram`. `KnotMosaicViewer` відображає SVG із панорамуванням, масштабуванням, плоскими ракурсами застосунку та SVG/PNG-знімками; `KnotViewer` делегує йому відображення.

### Коди планарних діаграм

[Специфікація PD](pd-code.uk.md) визначає дані `pd-code`: `convention`, `crossings` і необов’язкове `unlinkedComponents`. Реалізовані типи, схеми й семантична перевірка планарних систем обертання, узгодженості напрямків і кількості компонентів. PD має `viewSpace:"none"`; геометрія й відображення — окремі етапи.

### Коди Даукера–Тістлетвейта

[Специфікація DT](dt-code.uk.md) визначає `dt-code` для вузлів і зачеплень: явна конвенція знаків і плоскі або розділені за компонентами числові масиви парних міток обходу. Реалізовано схеми, перевірку перестановки й повний критерій планарної реалізовності. `viewSpace:"none"`; джерела й внесок задаються у звичайній оболонці. Геометрія та конвертації — окремі етапи.

## Ракурси й налаштування переглядача

`Knot` містить дані представлень, конструкції, стани й алгоритми, але **не містить ракурсів або параметрів відображення**. Поля відображення всередині представлення відхиляються JSON Schema.

Застосунок передає `view` (вбудований `ViewDefinition`, локальний `{id}` або `{ref}` із реєстру) та необов'язковий список ракурсів `views` безпосередньо до `KnotViewer`, `Knot2DViewer`, `Knot3DViewer` або `KnotMosaicViewer`. `initialCamera` — окремий параметр 3D-компонента. За відсутності явно обраного ракурсу переглядач використовує власний типовий вигляд. Плоский ракурс має вигляд `{mode:"plane",center:[x,y],height:додатне}`; поворот не підтримується. Налаштування експорту належать API переглядача, а не вузла. Див. [контракти переглядачів](viewer-contracts.uk.md).

## Самостійні контракти й ресурси

Незалежні схеми існують для сіткових і мозаїчних діаграм, кодів планарних діаграм, кодів Даукера–Тістлетвейта, геометрії 2D і 3D, представлення, конструкції, ракурсу, каталогу, типу представлення, типу предмета, призначення алгоритму, набору плиток, конвенції, мотузки й спорядження. Кожна опублікована схема включає тільки потрібні визначення й компілюється без кореневої схеми документа. Схеми генеруються з `src/core/contracts.json` командою `npm run build:schemas`.

`RawResourceDocument` вимагає `schema`, `schemaVersion`, `kind`, `resource`; необов’язкові `$schema`, `namespaces`, `dependencies`. Види: `catalog`, `representation-type`, `object-type`, `algorithm-purpose`, `tile-set`, `convention`, `view`, `construction`, `source`. Самостійний ресурс вимагає глобальний ID. `RawResourceRegistry` вимагає `schema`, `schemaVersion`, `resources:[{kind,resource}]`, може містити `$schema`, `namespaces`, `id`. Реєстр — звичайний документ, не сервер чи singleton. `RawRepresentationDocument` вимагає `schema`, `schemaVersion`, `representation`, може містити `$schema`, `namespaces`, `dependencies`, `subject`, `sources`.

Визначення каталогу вимагає глобальні `id`, `name`, `description`; необов’язкові `homepage`, `edition`, `identifierRules`. Правила підтримують `pattern` (ECMA-262 без прапорців) і `caseSensitive` (типово true). Порівняння ідентичності без урахування регістру, коли воно потрібне споживачу, зводить регістр лише ASCII A–Z; записані значення не змінюються. Валідатор перевіряє шаблони як записано, не шукає записи каталогу й не виводить тотожності. Для всього позначення шаблон обмежується `^`/`$`.

Залежності — записи `{kind,ref}`. Валідація `Knot` повідомляє нерозв’язані ресурсні потреби; перевірка оболонки реєстру/ресурсу не заявляє замкненості залежностей. Залежності користувацьких схем додатково відображаються неперевіреним статусом типу до підтримки його семантики.

## Джерела, внесок і ліцензія

Необов’язкові `Knot.sources` містять спільні визначення джерел із `id`; `Representation.sources` — вкладені описи або посилання з примітками конкретного використання. Необов’язкові плоскі `contributions` доступні на обох рівнях. Необов’язкова `license` належить тільки об’єкту `Knot`; ліцензія джерела залишається в його описі. Самостійний документ представлення може включати `sources` для локальних посилань. Ресурси підтримують додатковий вид `source`.

[Спільний контракт метаданих](sources.uk.md) визначає поля, ролі, перевірку, збереження при виділенні та конфлікти композиції. Відсутність метаданих не впливає на коректність; наявні посилання потребують розв’язання. Посилання не завантажуються автоматично. Визначення джерела не є каталогом ідентифікаторів або доказом тотожності вузла.

## Валідація та виділення

`Knot.validate(raw)` повертає `{valid:false,issues}` або `{valid:true,knot,warnings,complete,missingDependencies,uncheckedTypes}`. `valid` означає узгодженість відомих структур і розв’язуваних посилань; `complete` додатково вимагає всіх потрібних визначень та підтримуваної доменної семантики. Виділення вимагає повної перевірки документа; відображення — повної перевірки вибраного представлення та його залежностей. Валідація не змінює вхід і не завантажує дані. JSON Schema перевіряє структуру; валідатор додатково перевіряє області, унікальність, неперервність кривих, перестановки сіткових діаграм і сукупні бюджети. Це не доводить математичної тотожності чи практичної безпеки.

До обходу ресурсний профіль обмежує вкладеність до 64, кількість відвіданих значень до 262144, окремий рядок до 1048576 символів. Значення поза JSON, розріджені масиви, аксесори й цикли відхиляються. Додаткові структурні ліміти: 1024 представлення, 256 конструкцій/предметів/станів, 256 алгоритмів, 1024 кроки на алгоритм, 4096 точок на криву та 65536 точок у всьому `Knot`. Це захист реалізації, а не визначення всіх можливих доменних об’єктів.

`knot.select({representations?,algorithms?})` повертає незалежний самодостатній підготовлений `Knot` із вибраними алгоритмами, їхніми представленнями, потрібними повними конструкціями та визначеннями типів/призначень/наборів плиток/конвенцій/каталогів. Сторонні алгоритми й представлення не включаються. Після вкладення зовнішніх ресурсів глобальні посилання залишаються чинними. Виділяються лише підтримувані типи: невідомі URI-поля не можна безпечно переписати. Твердження поза початковим профілем, тому прихованого обходу зв’язків або пропусків тверджень немає.

`Knot.compose(parts,options?)` об’єднує фрагменти з однаковими ID документа й однаковими subjects після розгортання просторів імен. Конфлікти ID колекцій є помилками; пропущені поля не видаляють дані. Це не patch-формат і не об’єднання незалежних документів. Обидві операції повертають незалежні копії та повторно перевіряють результат.
