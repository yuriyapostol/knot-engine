# Джерела, внесок і ліцензування

Реалізовані необов’язкові метадані для всіх типів представлень. Вони описують атрибуцію та заявлені умови використання, не змінюють дані вузла й не доводять авторства, математичної істинності чи сумісності ліцензій.

## Розміщення

| Власник | Необов’язкові поля |
| --- | --- |
| Asset | `sources`, `contributions`, `license` |
| Representation | `sources`, `contributions` |
| KnotRepresentationDocument | Визначення `sources` для посилань свого представлення |

Обгортка `provenance` і поле `license` на рівні представлення не вводяться. Метадані належать оболонці представлення, а не його типоспецифічному `data`. Відсутність усіх метаданих зберігає чинну коректність і повноту. Для повноти явно вказані посилання на джерела повинні бути розв’язані.

## Джерела

Джерело описує матеріал, використаний для отримання даних. Вкладений запис має щонайменше `title` або `url` та такі необов’язкові поля:

| Поле | Значення |
| --- | --- |
| `title` | Непорожня назва джерела |
| `url` | Абсолютний HTTP(S) URL; перевірка його не завантажує |
| `authors` | Непорожній масив плоских записів `{name,email?,url?}` первісних авторів |
| `version` | Видання, редакція або ідентифікатор коміту |
| `license` | Заявлена ліцензія джерела `{name,url?}` |
| `locator` | Сторінка, поле таблиці, каталожний запис або рядок файла |
| `accessed` | Чинна календарна дата `YYYY-MM-DD` |
| `note` | Опис джерела або пояснення його використання |

Джерело може бути неопублікованим: назва може описувати власне креслення, приватні вимірювання чи друковану книгу. Автор джерела не стає автоматично учасником роботи над поточним об’єктом `Asset`.

Коренева `Asset.sources` містить спільні визначення з додатковим обов’язковим `id`, локальним або глобальним за звичайними правилами URI. Записи `sources` представлення мають одну з форм:

* Повне вкладене джерело без `id`.
* Посилання `{id:...}` на кореневе визначення або `{ref:...}` на явно переданий глобальний ресурс джерела. Посилання може містити `locator`, `accessed` і `note` для цього використання, але не перевизначає назву, URL, авторів, версію чи ліцензію джерела.

Вкладене визначення й посилання взаємовиключні. Примітка визначення залишається частиною джерела; примітка посилання описує конкретне використання й не перезаписує її. Так само розрізняються типові місце/дата звернення й значення конкретного використання. Кореневі визначення — спільна колекція, вони не застосовуються неявно до кожного представлення. Виділення зберігає тільки визначення, на які посилаються залишені представлення.

Зовнішні визначення використовують звичайні ресурси `kind:"source"`, реєстри, явні залежності й розгортання просторів імен. Відсутній локальний `id` — помилка. Відсутній глобальний `ref` потрапляє до нерозв’язаних залежностей виду `source` і робить перевірку неповною; неправильний вид ресурсу — помилка. URL джерел, авторів і ліцензій є звичайними URL, а не компактними ідентифікаторами чи прихованими залежностями. Самостійний документ ресурсу джерела вимагає глобальний ID.

Самостійний документ представлення може включати визначення `sources` для локальних посилань. Неявного реєстру й мережевого завантаження немає. Див. [повний приклад](../examples/assets/sources-contributions.json).

## Внесок

`contributions` — масив плоских записів, без вкладеного об’єкта людини/учасника й без окремого реєстру учасників.

| Поле | Значення |
| --- | --- |
| `name` | Обов’язкова непорожня назва людини, команди або організації |
| `email`, `url` | Необов’язкові контактна пошта й абсолютний HTTP(S) URL профілю |
| `roles` | Необов’язковий непорожній список різних кодів ролей |
| `date` | Необов’язкова чинна календарна дата `YYYY-MM-DD` |
| `note` | Необов’язковий опис виконаної роботи |

Ролі: `creation` — створення даних; `import` — перенесення з джерела; `conversion` — зміна формату/конвенцій; `editing` — редагування/виправлення; `validation` — перевірка. Достатньо імені й примітки. Email — контакт, а не ключ ідентичності. Контакти й ролі є заявами, а не перевіреними посвідченнями.

Кореневий внесок стосується об’єкта `Asset` загалом; внесок представлення — тільки цього представлення. Жоден список не копіюється на інший рівень неявно. Повторні роботи людини можуть мати окремі записи; це атрибуція, а не незмінний журнал редакцій чи історія для відновлення старих даних.

## Ліцензія

`Asset.license` має форму `{name,url?}` з обов’язковою непорожньою назвою й необов’язковим абсолютним HTTP(S) URL. Вона задає заявлену ліцензію зібраного об’єкта `Asset`. `source.license` описує вихідний матеріал. Жодна не перевизначає й не підставляє іншу автоматично. Відсутність означає «не зазначено», а не необмежене використання. Сумісність і право змінити ліцензію не виводяться й не перевіряються. Назвою може бути назва або код ліцензії; вбудований каталог і обов’язковий словник не вводяться.

## Збереження та перевірка

Виділення зберігає кореневі внески й ліцензію, метадані представлень і потрібні визначення джерел. Глобальні джерела стають самодостатніми через включення їхніх визначень у `sources` виділеного об’єкта `Asset` зі збереженням глобальних ID. Невикористані визначення не включаються. Метадані клонуються; вхідні об’єкти, порядок і URL джерел не переписуються. Лише ідентифікатори джерел підпорядковуються звичайному розгортанню просторів імен.

Композиція застосовує звичайні правила ідентичності й конфліктів до визначень джерел і представлень. Кореневі списки внесків об’єднуються в порядку входів, усуваючи тільки повністю однакові записи без урахування порядку ключів. Однакові ім’я/пошта не об’єднують різні внески. Різні метадані представлення з тим самим ID — конфлікт. Якщо ліцензія є тільки в одному фрагменті, вона зберігається; дві різні ліцензійні структури — конфлікт. Автоматичної перевірки правової еквівалентності чи зміни ліцензії немає.

Схеми закриті: відхиляються невідомі поля, змішані визначення/посилання, порожній обов’язковий текст і невідомі/повторні ролі. Структурні шаблони дат доповнюються календарною перевіркою під час виконання. HTTP(S) URL перевіряються синтаксично без мережі; email має базовий шаблон локальної частини/домену без пробілів, без перевірки доставки.

Бюджети реалізації: до 256 кореневих визначень джерел, 256 використань джерел на представлення, 128 авторів на джерело й 1 024 внесків на власника; до п’яти різних ролей на внесок. Порожні необов’язкові колекції дозволені, крім явно заданих `authors` і `roles`. Також діють загальні JSON-бюджети. Опубліковані окремі схеми [визначення джерела](../schema/source.schema.json), [внеску](../schema/contribution.schema.json) і [ліцензії](../schema/license.schema.json); потрібні визначення включено й до схем оболонок.

## Обґрунтування контракту та приклади

[Проєкт Asset](../../design/knot-asset-draft.uk.md) уже відокремлює колекції джерел від каталогів і передбачає джерела в представленнях. Реалізація дотримується цього напрямку без додаткової обгортки. Плоскі внески описують створення й редагування без графа ідентичностей. Глобальна ліцензія відповідає одиниці публікації; джерельні ліцензії залишаються окремою атрибуцією зовнішніх матеріалів.

Це рішення проєкту, а не твердження про таку саму структуру метаданих у зовнішніх базах вузлів. Числові конвенції й джерельні приклади залишаються у специфікаціях відповідних представлень. Документація має пояснювати суттєві рішення контракту, посилатися на відповідні визначення/реалізації, відрізняти запозичені конвенції від власних рішень і містити перевірені приклади. Відсутність зовнішнього джерела не можна видавати за зовнішню стандартизацію.

```json
{
  "sources": [{"title":"Власні вимірювання","note":"Записано з фізичного зразка."}],
  "contributions": [{"name":"Приклад редактора","roles":["editing","validation"],"note":"Виправлено й перевірено координати."}]
}
```

Це фрагмент метаданих, а не повне представлення. Критерії приймання: всі підтримувані типи даних, вкладені/локальні/глобальні джерела, нерозв’язані посилання, календарні дати й контакти, обидва рівні внеску, виділення джерел, конфлікти композиції та відсутність необов’язкових метаданих.
