# Спільні та вкладені ресурси

Нотатка пояснює реалізований підхід до ресурсів. Точні поля й обмеження визначені [контрактом даних](../v1/specifications/knot.uk.md), [контрактом метаданих](../v1/specifications/sources.uk.md) та окремими схемами. [Відкриті проєктні питання](knot-draft.uk.md) стосуються додаткових понять.

## Ідентичність і простори імен

Ідентифікатори проєкту використовують `https://yuriyapostol.github.io/knot-engine/v1/`. Ідентичність ресурсу не залежить від шляху файла, адреси документації чи випуску. Ідентифікатори інтеграцій належать Knot Engine; зовнішні стандарти зберігають власні ідентичності. URI не означає публікації або завантаження з мережі.

```json
{
  "namespaces": {
    "knot-engine": "https://yuriyapostol.github.io/knot-engine/v1/"
  }
}
```

Оголошений `knot-engine:representation-types/pd-code` розгортається конкатенацією URI простору й суфікса. Локальні ID зберігають визначену область. Префікси `http`, `https` та `urn` зарезервовані; неоголошені префікси є помилкою. Глобальні ID порівнюються після розгортання. Текст, URL джерел і довільні невідомі дані не переписуються. JSON Schema `$id`/`$ref` та редакторський `$schema` зберігають звичайну семантику URI.

## Оболонки й розміщення

`RawResourceDocument` використовує `schema: "ResourceDocument"`, `schemaVersion: 1`, `kind` і `resource`, з необов’язковими `$schema`, `namespaces` та `dependencies`. Самостійний ресурс потребує глобального ID. `RawResourceRegistry` використовує `schema: "ResourceRegistry"` та записи `resources` із `kind`/`resource`; необов’язкові поля — `$schema`, `namespaces` та `id`.

| Вид | Визначення | Розміщення |
| --- | --- | --- |
| `catalog` | Система ідентифікації та правила позначень | `RawKnot.catalogs`, явний реєстр |
| `representation-type` | Схема даних і семантична специфікація | `RawKnot.representationTypes`, явний реєстр |
| `object-type` | Контракт даних предмета конструкції | `RawKnot.objectTypes`, явний реєстр |
| `construction` | Конкретні предмети й необов’язкові іменовані стани | `RawKnot.constructions`, явний реєстр |
| `source` | Походження даних, автори й ліцензія джерела | `RawKnot.sources`, явний реєстр |
| `view` | Іменована плоска або просторова камера | `views` застосунку, явний реєстр |

Конструкції можна вкладати або включати через `{ref: URI}`. Локальні `{id}` та глобальні `{ref}` посилання взаємовиключні. Ракурси належать застосунку й передаються компонентам окремо. Усі переглядачі отримують контекст вузла, а не самі дані ресурсу.

Різні визначення з однаковими видом і розгорнутим URI конфліктують; однакові JSON-визначення можна дедуплікувати без урахування порядку ключів об’єкта. Реєстри передаються явно, включно з `STANDARD_RESOURCES`; singleton або resolver не завантажує відсутні визначення. Відсутні залежності й неперевірені типи перешкоджають повній валідації. Перевірка самої оболонки ресурсу/реєстру не встановлює транзитивної замкненості.

## Каталоги, типи й конструкції

Каталог визначає систему ідентифікації, а не перелік її записів. Його назва є підписом, а не ключем пошуку. `identifierRules` перевіряє синтаксис позначення; це не доводить існування запису або еквівалентності вузла. Видання, які повторно використовують позначення для іншого предмета опису, потребують різних ідентичностей.

Типи представлень і предметів указують `dataSchema` та семантичну `specification`. Зовнішні схеми передаються явно через параметри валідації; вкладені схеми оголошують діалект. Схема не встановлює семантичний валідатор, імпортер або переглядач. `viewSpace` описує сумісність ракурсів представлення незалежно від фізичної вимірності предмета опису.

Конструкція містить конкретні предмети з локальними ID й необов’язкові іменовані стани. Топологія мотузки, кінці, довжина й діаметр є доменними даними. Тип карабіна відрізняється від його ролі опори. Матеріал, обмеження й ролі в окремих станах потребують подальших доменних контрактів.

## Ракурси застосунку

`ViewDefinition` вимагає `id`, `name`, `space` та `camera`; `description` необов’язковий. Просторові камери використовують повні режими `fit` або `fixed` з перспективною чи ортографічною проєкцією. Плоскі камери використовують `mode: "plane"`, `center` і додатний `height`, без повороту. Вибір і перевизначення описані в [контрактах переглядачів](../v1/specifications/viewer-contracts.uk.md).

Наприклад, застосунок може передати це значення як параметр `view`:

```json
{
  "id": "front",
  "name": "Front",
  "space": "space",
  "camera": {
    "mode": "fit",
    "direction": [0, 0, 1],
    "up": [0, 1, 0],
    "projection": { "kind": "perspective", "fovY": 0.7853981633974483 }
  }
}
```

Те саме визначення можна зберегти в масиві `views` застосунку й вибрати через `view: {id: "front"}`. Глобальний пошук `{ref}` використовує явні реєстри й оголошені простори імен. Відсутність `view` означає типові параметри переглядача; сам список ракурсів нічого не вибирає. Взаємодія змінює локальний стан переглядача й залишає дані вузла незмінними.

## Приклад самостійного каталогу

Цей вигаданий навчальний каталог демонструє оболонку ресурсу. Він не є визначенням інтеграції KnotInfo. Його `resource` також можна помістити в `RawKnot.catalogs`.

```json
{
  "schema": "ResourceDocument",
  "schemaVersion": 1,
  "namespaces": {
    "knot-engine": "https://yuriyapostol.github.io/knot-engine/v1/"
  },
  "kind": "catalog",
  "resource": {
    "id": "knot-engine:catalogs/training-knots",
    "name": "Training knots",
    "description": "An example registry where each described construction has a unique designation.",
    "identifierRules": { "caseSensitive": true, "pattern": "^A-[0-9]{3}$" }
  }
}
```

Визначення джерел фіксують походження окремо від каталогів. Внески залишаються плоскими списками вузла або представлення, а ліцензія вузла описує одиницю публікації. Див. [джерела та внесок](../v1/specifications/sources.uk.md).
