# Спільні та вкладені сутності KnotAsset

**Стан реалізації:** початковий профіль (просторові криві, сіткові діаграми, мозаїчні діаграми, коди планарних діаграм, конструкції, процедури, ресурси й камери) описано в [чинній специфікації](../v1/spec/knot-asset.uk.md). Цей ширший проєкт містить також відкладені можливості; чинна специфікація визначає точні підтримувані поля.

Статус: проєктний матеріал, що деталізує [архітектурну чернетку](knot-asset-draft.uk.md). Самостійні ресурси й можливість вкладення реалізовано в початковому профілі. [Чинна специфікація](../v1/spec/knot-asset.uk.md) визначає підтримувані поля; додаткові деталі нижче залишаються пропозиціями. `schemaVersion: 1` і версії пакета не змінюються; сумісність із попередньою структурою не вимагається.

Структура сайту й правила спільних випусків: [публікація та версії](publication.uk.md).

## 1. Простір імен

Базова адреса власних ідентифікаторів: `https://yuriyapostol.github.io/knot-engine/v1/`.

| Шлях від бази | Призначення |
| --- | --- |
| `guide/` | Інструкції та навчальні матеріали; контракти компонентів і функцій — у `spec/` |
| `spec/` | Специфікації форматів, семантика та правила обробки |
| `schema/<contract>.schema.json` | JSON Schema самостійного контракту |
| `catalogs/<name>` | Визначення системи каталожних позначень |
| `representation-types/<name>` | Визначення семантики представлення |
| `categories/<name>` | Терміни класифікації |
| `relations/<name>`, `properties/<name>` | Визначення відношень і характеристик |
| `object-types/<name>`, `tile-sets/<name>` | Контракти предметів і набори плиток (їхні детальні схеми потребують окремого опрацювання) |
| `views/<name>`, `constructions/<name>` | Повторно використовувані ракурси й конструкції |
| `examples/<name>` | Ідентичність демонстраційних сутностей |

Це простір імен проєкту, а не обіцянка, що кожна адреса вже опублікована. URI визначення типу і URI його JSON Schema мають різні ролі. Ідентифікатори інтеграцій зовнішніх каталогів у цьому просторі належать Knot Engine, а не видавцям каталогів. Зовнішні стандарти й джерела зберігають власні справжні URI.

У прикладах нижче `schema` — назва контракту, `schemaVersion` — покоління його структури, `$schema` — необов’язкове посилання на відповідну JSON Schema для інструментів. Суперечність цих трьох значень є помилкою. Спільне `1` не заважає незалежним точкам входу підсхем.

### Простори імен — погоджене рішення

`KnotAsset`, `KnotRepresentationDocument`, `KnotResourceDocument` і `KnotResourceRegistry` підтримують кореневий словник `namespaces`. Ключ — префікс, значення — повний URI простору імен. Для проєкту використовуємо явне оголошення:

```json
{
  "namespaces": {
    "knot-engine": "https://yuriyapostol.github.io/knot-engine/v1/"
  }
}
```

Глобальний ідентифікатор записується як `knot-engine:назва`, наприклад `knot-engine:representation-types/pd-code`. Розгортання додає суфікс після першої двокрапки до URI оголошеного простору. Це підстановка префікса, а не розв’язання відносного шляху: `../` не є механізмом переходу між просторами. Конкретний приклад розгортається в `https://yuriyapostol.github.io/knot-engine/v1/representation-types/pd-code`.

- `namespaces` обов’язковий, якщо документ використовує скорочені глобальні ідентифікатори. При використанні лише повних URI його можна опустити. Неявного стандартного префікса й вкладених перевизначень немає.
- Рішення замінює попередню пропозицію `base` для ідентичності сутностей. Звичайні відносні шляхи не є глобальними ідентифікаторами. Адреса файла, сторінки чи документа не впливає на ідентичність.
- Назви полів залишаються незмінними: `id`, `type`, `catalog`, `category`, `ref` тощо. Поле `local` замість `id` не вводимо. Локальний запис залишається, наприклад, `id: "rope-a"`; посилання з областю може мати вигляд `{kind: "object", construction: {id: "setup-a"}, id: "rope-a"}`.
- Локальні ID не розгортаються через `namespaces`. Їхню область задає контракт: документ, конструкція, процедура тощо. Глобальні URI-поля приймають оголошене `prefix:suffix` або повний URI; звичайне `rope-a` у такому полі не стає глобальним автоматично. Каталожні `value`, текст і довільні рядки `data` не обробляються як ідентифікатори.
- Повний URI і скорочення того самого URI ідентифікують одну сутність. Префікс є локальним псевдонімом простору; порівняння й виявлення конфліктів виконуються після розгортання.
- Глобальне ім’я не означає зовнішнього завантаження: визначення може бути вкладене в об’єкті `KnotAsset` або надане реєстром. `namespaces` описує ідентичність, а не список імпортованих даних.
- При виділенні частини переносимо використані оголошення просторів або розгортаємо відповідні поля в повні URI. При композиції спочатку враховуємо словник кожного документа. Однаковий префікс із різними URI не можна мовчки об’єднувати: потрібно явно перейменувати префікс із переписуванням його використань або зберегти повні URI.
- Схеми URI та префікси не повинні конфліктувати. Деталі граматики ще потребують остаточного контракту; робоче правило — резервувати підтримувані схеми повних URI (`http`, `https`, `urn`) і відхиляти неоголошений префікс, не трактуючи друкарську помилку як довільну схему URI.

Словник — механізм `KnotAsset`, а не оголошення документа JSON-LD. Власний resolver обробляє лише визначені контрактами поля. JSON Schema, включно із вкладеними схемами, зберігає стандартну семантику `$id`/`$ref`; наші префікси в них не підставляються. Редакторський `$schema` також залишається повним URI. Звичайні URL джерел та зображень можуть зберігатися повністю; окремий механізм відносних адрес файлів цим рішенням не вводиться.

Невідомий тип із неописаними URI-полями не можна автоматично переписувати під час перенесення між словниками. Зміна URI простору без переписування залежних ідентифікаторів змінює їхню ідентичність.

## 2. Одна сутність — один контракт

Для кожного ресурсу є незалежна схема даних: `CatalogDefinition`, `RepresentationTypeDefinition`, `ViewDefinition`, `Construction`. Ці самі дані можна використати:

1. Без оболонки як аргумент вузького компонента.
2. У самостійному документі з назвою схеми.
3. У відповідній колекції об’єкта `KnotAsset` або явно переданого реєстру.

Запропонована оболонка `KnotResourceDocument` має обов’язкові `schema`, `schemaVersion`, `kind`, `resource`; необов’язкові `$schema`, `namespaces`, `dependencies`. `kind` вибирає точну схему `resource`: `catalog`, `representation-type`, `view`, `construction`. Оболонка не додається до кожного вкладеного запису. `dependencies` — масив `{ "kind": <вид ресурсу>, "ref": <URI, абсолютний після розв’язання> }`; він оголошує потрібні зовнішні визначення, але не завантажує їх.

Реєстр `KnotResourceRegistry` — документ із `schema`, `schemaVersion`, необов’язковими `$schema`, `namespaces`, `id` та масивом `resources`. Кожен запис має `kind` і `resource`, як у самостійній оболонці. Реєстр може бути файлом або відповідним об’єктом застосунку; сервер чи глобальний singleton не потрібен.

Розташування в об’єкті `KnotAsset`:

| Поле | Вміст |
| --- | --- |
| `catalogs[]` | Вкладені `CatalogDefinition` |
| `representationTypes[]` | Вкладені `RepresentationTypeDefinition` |
| `constructions[]` | `Construction` або `{ "ref": "<URI>" }` |
| `representations[].views[]` | `ViewDefinition` або `{ "ref": "<URI>" }` |
| `dependencies[]` | Зовнішні залежності, які має надати споживач |

`subject.identifiers[].catalog` і `Representation.type` вже є посиланнями на визначення. Тому окремий запис `{ref}` у `catalogs` чи `representationTypes` не потрібен. Відсутність цих колекцій звична, якщо визначення надані реєстром. Вкладати можна й загальновідоме визначення — наприклад, для автономного експорту.

У `constructions` і `views` форма `{ref}` означає саме включення зовнішньої сутності до набору доступних конструкцій або ракурсів. Вона не допускає додаткових полів для неявного перевизначення ресурсу. Власний змінений ресурс отримує власну ідентичність; зв’язок із вихідним можна зафіксувати окремо.

### Розв’язання і перевірка

- Абсолютні URI порівнюються точно. `name` не є ключем і не запускає евристичний пошук.
- Реєстр передається явно. Посилання не запускає мережевий запит або виконання коду.
- Локальні ID вкладених конструкцій, ракурсів, станів і предметів дозволені. Зовнішній `{ref}` містить URI, абсолютний після розгортання через `namespaces`; локальні посилання мають явну форму `{ "id": "setup-a" }`. Ці форми взаємовиключні.
- Публікація локальної конструкції окремим ресурсом потребує глобального ID та переписування посилань. ID її внутрішніх предметів і станів залишаються локальними до конструкції.
- Два різні визначення одного глобального ID — конфлікт, навіть якщо одне вкладене. Точні дублікати після порівняння JSON без урахування порядку ключів об’єктів можна дедуплікувати; семантичну еквівалентність різних описів не вгадуємо.
- Нерозв’язане посилання не заважає прочитати оболонку, але не дозволяє оголосити документ самодостатнім або повністю семантично перевіреним. Результат перевірки має містити перелік відсутніх залежностей.
- Самодостатній експорт включає транзитивно потрібні визначення та ресурси. Внутрішні цикли обходяться один раз за ID. Повний реєстр не копіюється.
- Дані вузького компонента можуть бути вже перевірені й розв’язані викликачем: засіб візуалізації мозаїки не повинен знати про каталоги чи конструкції, яких його дані не потребують.

## 3. CatalogDefinition

Обов’язкові `id` (глобальний URI, абсолютний після розгортання через `namespaces`), `name`, `description` (непорожні рядки). `description` визначає предмет каталогу та суттєві розрізнення, зокрема орієнтацію, дзеркальність і редакцію, якщо вони впливають на позначення.

Необов’язкові `homepage` (повний URL), `edition` (рядок), `identifierRules` з полями `caseSensitive` (boolean, типово `true`) та `pattern` (рядок регулярного виразу ECMA-262 без прапорців). Шаблон перевіряється як записано; для всього рядка автор задає `^` і `$`. При `caseSensitive: false` порівнюються лише ASCII A–Z/a–z без урахування регістру; інші символи порівнюються точно. Інші правила нормалізації потребують окремого розширення. Значення позначення зберігається без змін.

`subject.identifiers` містить `{catalog: URI, value: string}`. Пара визначає запис у каталозі; відповідність форми не доводить існування запису або тотожності вузлів. Каталог не містить усі свої записи, не замінює джерело твердження чи словник категорій. Якщо редакція повторно використовує позначення для іншого предмета, їй потрібна інша ідентичність каталогу.

## 4. RepresentationTypeDefinition

Обов’язкові:

| Поле | Зміст |
| --- | --- |
| `id` | Глобальний URI; `Representation.type` посилається на той самий URI після розгортання через `namespaces` |
| `name`, `description` | Назва й семантика представлення |
| `dataSchema` | `{ "ref": "<URI схеми>" }` або `{ "inline": <об’єкт JSON Schema> }` |
| `specification` | URI тексту з конвенціями та семантичними правилами, яких недостатньо описати JSON Schema |

Вкладена схема має використовувати явно зазначений діалект JSON Schema. Її зовнішні `$ref` також потребують переданого реєстру схем; вкладення лише головної схеми не гарантує автономність.

Необов’язкове `viewSpace`: `none`, `plane` або `space`, типово `none`. Це сумісність із базовими ракурсами, а не фізична розмірність предмета. `specification` визначає індексацію, орієнтацію, топологічні обмеження й залежності конкретного `data`. Для нового типу одного URI недостатньо: структурна схема і семантика обов’язкові.

Реєстрація визначення не додає засобу візуалізації, імпортер або математичного валідатора. Застосунок окремо зіставляє ID типу зі своїми реалізаціями. Невідомий тип можна зберігати, але не оголошувати підтримуваним. KnotScape і SnapPy — походження/інструменти, а не самі собою формати даних.

Пропозиція використовувати URI в `type` замінює короткі рядки чернетки. Короткі назви залишаються підписами для людей. Префікси оголошуються явно у `namespaces`.

## 5. ViewDefinition і preferredView

`ViewDefinition` має обов’язкові `id` (локальний або глобальний), `name`, `space` (`plane` або `space`), `camera`. Необов’язкове `description`. Визначення не містить посилання на предмет опису і може передаватися без об’єкта `KnotAsset`. Усі координати належать системі даних того представлення, до якого застосовують ракурс.

Базовий контракт `camera` — об’єднання трьох явних форм:

| `mode` | Обов’язкові параметри | Семантика |
| --- | --- | --- |
| `fit` при `space: space` | `direction`, `up`, `projection` | Два ненульові неколінеарні XYZ-вектори; напрямок від фокуса до камери; вміщення геометрії |
| `fixed` при `space: space` | `position`, `target`, `up`, `projection` | XYZ-позиція, відмінна від цілі; `up` не паралельний напрямку погляду |
| `plane` при `space: plane` | `center`, `height`, `rotation` | XY-центр, додатна висота видимої області в координатах даних, поворот у радіанах проти годинникової стрілки в площині даних |

Усі числа скінченні. Для 3D `projection` — `{kind: "perspective", fovY: число}` з `0 < fovY < π` у радіанах, або `{kind: "orthographic"}`. Для `fixed` ортографічна форма додатково вимагає додатний `height`. Співвідношення сторін задає область перегляду; near/far обчислює засіб візуалізації. `fit` бере центр обмежувального паралелепіпеда і вміщує всю геометрію; необов’язковий `padding` є множником розміру, не меншим за 1, типово 1.1. У `fixed` та `plane` padding не застосовується. Ненормовані direction/up нормалізуються при застосуванні, без зміни записаних даних.

Це базовий контракт камери, а не завершена модель освітлення, матеріалів, анімації чи всіх параметрів компонента перегляду. Майбутні параметри оформлення потребують власної типізації. Їх не слід зараз додавати довільним нетипізованим об’єктом.

`Representation.views` включає доступні ракурси вкладенням або посиланням. `defaultView` — необов’язкове `{id: id}` або `{ref: URI}` на один із них. `preferredView` залишається компактною незалежною підказкою `{direction, up}` лише для 3D; вона не містить відстані, матеріалів чи обов’язкового запису в реєстрі.

Порядок початкового вибору: явно вибраний застосунком ракурс → `defaultView` → `preferredView` з автоматичним вміщенням → типовий ракурс компонента. Кожний крок вибирає повний режим камери; поля різних режимів не змішуються неявно. Після вибору користувач може змінювати камеру без редагування об’єкта `KnotAsset`. Ракурс у системі `space` несумісний із представленням `plane`/`none`.

## 6. Construction

Конструкція — конкретний набір предметів, не шаблон класу «будь-які дві мотузки». Визначення типів предметів і можливі шаблони конструкцій — окремі майбутні контракти.

Мінімальний `Construction`: обов’язкові `id`, непорожній `objects`; необов’язкові `name`, `description`, `states`. Предмет має локальний унікальний `id`, `type` (URI контракту предмета); його додаткові дані перевіряє цей контракт. Для мотузки чернетка передбачає `topology: open | closed`; відкрита має рівно два різні `ends[].id`, замкнена не має кінців. Матеріал, фізичні умови, ролі та обмеження станів ще потребують окремого доменного опрацювання.

Мінімальний стан має локальний унікальний `id`, необов’язкові `name`, `description`. Це іменований стан, а не довільний об’єкт для всіх майбутніх властивостей. Конструкція не залежить від наявності геометрії. Процедури та представлення посилаються на конструкцію; конструкція не потребує зворотних посилань на всіх своїх споживачів.

Посилання на конструкцію у `target` або процедурі — `{id: id}` чи `{ref: URI}`; посилання на її стан додатково має `kind: "state"` та `id` стану. Ідентичні локальні `rope-a` у різних конструкціях — різні предмети. Спільний глобальний ресурс не можна незалежно змінювати через один із об’єктів `KnotAsset`, які на нього посилаються.

## 7. Приклад вкладеного і зовнішнього ракурсу

Це ілюстрація полів представлення, не повний документ і не твердження про вже опублікований ресурс:

```json
{
  "views": [
    { "ref": "https://yuriyapostol.github.io/knot-engine/v1/views/front" },
    {
      "id": "author-angle",
      "name": "Авторський ракурс",
      "space": "space",
      "camera": {
        "mode": "fit",
        "direction": [1, 1, 2],
        "up": [0, 1, 0],
        "projection": { "kind": "perspective", "fovY": 0.7853981633974483 }
      }
    }
  ],
  "defaultView": { "id": "author-angle" }
}
```

Самостійне визначення каталогу:

```json
{
  "schema": "KnotResourceDocument",
  "schemaVersion": 1,
  "namespaces": {
    "knot-engine": "https://yuriyapostol.github.io/knot-engine/v1/"
  },
  "kind": "catalog",
  "resource": {
    "id": "knot-engine:catalogs/training-knots",
    "name": "Навчальний каталог",
    "description": "Демонстраційний реєстр окремо описаних конструкцій; кожна має унікальне позначення.",
    "identifierRules": { "caseSensitive": true, "pattern": "^A-[0-9]{3}$" }
  }
}
```

`resource` без змін можна помістити в `asset.catalogs`. Реальний опис KnotInfo ще потребує перевірки семантики його записів; навчальний приклад не видається за таке визначення.
