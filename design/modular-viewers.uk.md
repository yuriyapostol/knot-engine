# Архітектура модульних переглядачів (проєкт контракту)

**Статус:** погоджений напрям, специфікація першого етапу. Реалізація в коді ще не виконана. Поточний публічний API визначено в [components](../v1/specifications/components.uk.md). Цей документ не оголошує запропоновані API вже доступними.

## Мета і межі

`KnotViewer` є універсальним композитором: перевіряє цілісність документа, обирає представлення, розгортає URI типу через `namespaces`, знаходить реалізацію в явно наданому або типовому реєстрі, передає їй дані та контекст і делегує методи й події. Він не імпортує Three.js і не містить умов побудови геометрії окремих форматів.

`Knot3DViewer` відображає `spatial-curve`; `KnotMosaicViewer` відображає `mosaic-diagram`. Обидва придатні до прямого використання з типізованими даними представлення та, за потреби, явним доменним контекстом. Наявність визначення `representation-type` не означає наявності переглядача. Невідомі типи, відсутній переглядач, неповні залежності та невалідні дані діагностуються окремо.

## Межі відповідальності

- `core`: типи, JSON Schema, доменна семантика, валідація, URI, ресурси, вибір та підготовка даних без Vue, Three.js, DOM чи мережі.
- `KnotViewer`: перевірка, вибір, маршрутизація, спільні стани, слоти та делегування. Перевірка має завершитися до виділення WebGL.
- Спеціалізований переглядач: власний рушій, взаємодія, lifecycle, знімки, специфічні налаштування. 3D-геометрія й камера залишаються в просторовому модулі; мозаїка може використовувати SVG.
- Реєстр: відображення **повного розгорнутого URI** на фабрику/компонент та його можливості; без глобального змінного стану. Застосунок може передати власні реєстрації й явно перевизначити стандартні. Реєстр не завантажує модулі чи дані через мережу.

## Контракт переглядача

Спільні входи: `data`, необов'язковий доменний контекст, `settings`, `label`, `description`, `locale`, `theme`, `active`, `interactive`, `showControls`. Входи незмінні; заміна об'єкта оновлює відображення. Типи `data` і `settings` залежать від реалізації. Контекст не повинен вимагати цілого `KnotAsset`, коли достатньо даних одного представлення.

Спільні стани: `empty`, `initializing`, `ready`, `error`. Спільні події: `ready`, `error`, `view-change`. `camera-change` — спеціалізована подія 3D. Спільні методи: `resetView()`, `fitToView()`, `capture(options?)`. Непідтримувані методи та можливості не імітуються: підтримка zoom, orbit, pan, edit і конкретних форматів знімка оголошується явно. Точні TypeScript сигнатури, типізовані payload і перелік кодів помилок потрібно закріпити в нормативній специфікації до рефакторингу.

Керування активністю, видимістю, доступністю, SSR fallback, вивільненням ресурсів, відновленням після помилки та незалежністю екземплярів має зберегти поведінку чинного 3D-переглядача.

## Параметри перегляду

Параметри відображення передаються **окремо від** `KnotAsset` і `Representation.data`. До них належать камера, проєкція, zoom/pan, кадрування, оформлення та взаємодія. Система координат, масштаб фізичних одиниць, топологія, конвенції плиток, авторська геометрія, конструкції та стани залишаються доменними даними. Обертання ракурсу не змінює матрицю мозаїки; дзеркальне перетворення топологічної діаграми не є просто параметром камери.

Поточні `Representation.views`, `defaultView`, `preferredView` та входи `view`/`initialCamera` потребують узгодженого перегляду й перенесення ролі налаштувань до окремого контракту. Іменовані набори можуть зберігатися поза активом із посиланням на ID представлення; формат зберігання та пріоритети застосування потрібно затвердити до зміни схем. Відсутність settings має давати документовані типові значення. Знімки й екран повинні однаково інтерпретувати settings. Зміна ракурсу не мутує дані вузла.

## API, CSS і залежності

Зберегти `knot-engine` як один пакет із прямими експортами `KnotViewer`, `Knot3DViewer`, `KnotMosaicViewer`; розглянути `knot-engine/3d` та `knot-engine/mosaic` для окремого завантаження. Перевірити, що імпорт мозаїки не включає Three.js. Core лишається окремим `knot-engine/core`.

CSS: `.knot-engine-v1-viewer`, `.knot-engine-v1-3d-viewer`, `.knot-engine-v1-mosaic-viewer` і відповідні `--knot-engine-v1-<component>-*`. Глобальні стилі заборонені; різні покоління й компоненти мають співіснувати. Пряме використання спеціалізованих переглядачів не повинно вимагати обгортки `KnotViewer`.

## Послідовність

1. Затвердити нормативні TS/JSON контракти settings, registry, capabilities, подій та помилок; погодити міграцію ракурсів.
2. Винести поточний Three.js рушій у `Knot3DViewer`, перетворити `KnotViewer` на композитор, оновити документацію й приклади.
3. Додати SVG `KnotMosaicViewer` для фіксованого Lomonaco–Kauffman набору 0–10 без зміни кодів плиток; редактор не входить у цей етап.
4. Після перевірки на двох рушіях розширювати registry й типи представлень.

## Критерії приймання

- 3D працює безпосередньо та через композитор; збережені камера, touch, keyboard, PNG, fallback, SSR, lifecycle та обмеження ресурсів.
- Мозаїка працює безпосередньо та через композитор; перетини 9/10 і неперетинні плитки 7/8 малюються згідно з конвенцією.
- Повний і скорочений URI одного типу обирають той самий переглядач; непідтримуваний тип повертає явну діагностику.
- Два екземпляри одного представлення мають незалежні налаштування; дані та вхідні об'єкти не мутуються.
- Знімки відображають ті самі налаштування, що й екран; непідтримувані можливості діагностуються.
- Мозаїчний entry point не підтягує Three.js; core залишається незалежним від UI.
- Перевірки охоплюють типізацію, модульні тести, браузер, SSR, npm tarball, збірку сайту й ізоляцію CSS.
- Версія пакета `0.1.0` та `schemaVersion: 1` поки не змінюються; тимчасова підтримка старого API не потрібна.
