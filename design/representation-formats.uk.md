# Представлення KnotInfo: джерела даних і пропозиції контрактів

Статус: дослідження для [нової структури `KnotAsset`](knot-asset-draft.uk.md). Перевірено 12 жовтня 2026 року. Нижче явно розділені вихідні формати та запропоновані JSON-адаптації. Наявність опису не означає, що імпортер чи засіб візуалізації вже реалізований.

## 1. Що насправді є на сторінці

На [сторінці діаграм 3_1](https://knotinfo.org/diagram_display.php?3_1) є такі подання:

| Підпис на сторінці | Реальні доступні дані | Пропозиція для `KnotAsset` |
| --- | --- | --- |
| KnotScape | PNG | `diagram-image`; окремо структурна плоска діаграма, якщо отримано її вихідні дані |
| SnapPy | SVG із кубічними кривими Безьє | `diagram-image`; для редагованої діаграми — імпорт SnapPea/PLink projection |
| 3D | Масив XYZ у JavaScript і параметри побудови кривої | `spatial-curve` з явно заданою інтерполяцією |
| Сіткові діаграми (Grid) | SVG; у записі вузла також список координат | `grid-diagram` з профілями кодування |
| Minimal mosaic and tile diagrams | PNG; структурні мозаїки є в авторському репозиторії | `mosaic-diagram` з визначеним набором плиток |

Назви типів у тексті скорочені для читання. Їхні ID мають форму `https://yuriyapostol.github.io/knot-engine/v1/representation-types/<name>`.

PNG/SVG зберігають вигляд, але не гарантують наявності топологічних даних. Назва програми є походженням представлення. Мінімальний розмір мозаїки та мінімальна кількість непорожніх плиток — різні властивості, не обов’язково різні типи представлення.

## 2. Плоскі діаграми: зображення, геометрія і PD

### Оригінальні зображення

Перевірені [KnotScape PNG](https://knotinfo.org/Diagrams_All_Folders/diagrams_knotscape/3_1.png) і [SnapPy SVG](https://knotinfo.org/Diagrams_All_Folders/diagrams_snappy/3_1.svg). SVG для `3_1` має `viewBox="14.000 14.000 472.000 472.000"` і шість `path` з командами `M`/`C`. Розриви ліній передають проходження знизу візуально; окремого графа перехресть або PD-коду в цьому файлі немає.

Пропонований `diagram-image.data`: обов’язкові `mediaType` (`image/png` або `image/svg+xml` у початковому профілі) та `content`, рівно одна форма `{uri: URL}` або `{base64: string}`. Необов’язковий `description`. Це наша контейнерна структура для наявного стандартного файла, а не новий формат топології. Файл за URI є зовнішньою залежністю; автономний експорт мусить включити його байти. Топологічний аналіз такого представлення не обіцяється.

На сторінці дзеркальні KnotScape, SnapPy та Grid отримано CSS `scaleX(-1)` над тим самим файлом. Це не додаткова вихідна модель. Відображення, що змінює дзеркальність діаграми, не можна приховати у звичайному обертанні камери й автоматично вважати тим самим предметом опису.

### Реальний редагований формат SnapPea/PLink

[PLink](https://snappy.computop.org/plink.html) працює з плоскою діаграмою як із вершинами, спрямованими відрізками й перехрестями. Точний текстовий формат підтверджується парними методами `_from_string` та `SnapPea_projection_file` у [вихідному коді](https://github.com/3-manifolds/PLink/blob/33715420c59090cda4ae8bd13745ba2a442a1d63/src/plink/manager.py).

Послідовність у звичайному файлі:

```text
% Link Projection
<кількість компонентів>
<індекс першої вершини> <індекс останньої вершини>  (для кожного компонента)
<кількість вершин>
<x> <y>                                              (для кожної вершини)
<кількість спрямованих відрізків>
<індекс початкової вершини> <індекс кінцевої вершини>  (для кожного відрізка)
<кількість перехресть>
<індекс нижнього відрізка> <індекс верхнього відрізка> (для кожного перехрестя)
<індекс активної вершини або -1>
```

Індекси починаються з нуля. Для замкненого компонента перший і останній індекси збігаються. Варіант `% Virtual Link Projection` додає перед парою індексів перехрестя `v` або `r`; це інша семантика, яку не можна мовчки відкинути.

**Пропозиція адаптації:** `planar-diagram.data` містить `vertices: [x,y][]`, `edges: [start,end][]`, `crossings: {under,over}[]` і `components: {start,end}[]`, плюс явну систему 2D-координат. Початковий профіль охоплює лише звичайні перехрестя. Віртуальні потребують окремої форми й перевірок; імпортер має відмовлятися від непідтримуваного варіанта. Активна вершина є станом редактора, не топологією.

Обґрунтування: ця адаптація зберігає координати та явне over/under, потрібні редактору й засіб візуалізації. Вона не вигадує layout з одного PD-коду. Перевірки: межі індексів, ненульові відрізки, послідовність компонентів, відповідність заявлених перехресть перетинам геометрії, відсутність неоднозначних дотиків/накладань. Точне правило числової похибки ще потрібно визначити. Оригінальний текст доцільно зберігати як джерело; writer PLink форматує координати цілими числами, тому довільний зворотний експорт дробової геометрії не гарантовано точний.

На дослідженій сторінці KnotInfo немає посилання на вихідний `.lnk` саме для зображення `3_1`. Наявність формату PLink не доводить, що конкретний SVG можна без втрат перетворити назад у нього.

### PD і DT як окремі представлення

[Запис KnotInfo для 3_1](https://knotinfo.org/results.php?searchmode=singleknot&submittype=singleknot&singleknot=3_1) містить:

```json
{
  "pd": [[1, 5, 2, 4], [3, 1, 4, 6], [5, 3, 6, 2]],
  "dt": [4, 6, 2]
}
```

Це витяг двох вихідних значень, не пропозиція зберігати їх разом у одному `data`.

Реалізований [контракт PD](../v1/spec/pd-code.uk.md) містить фіксований `convention`, `crossings` як четвірки додатних цілих міток і необов’язкове `unlinkedComponents`. Він зберігає джерельні мітки та описує комбінаторну діаграму, а не координати рисунка. Конвенція [KnotInfo](https://knotinfo.org/descriptions/pd_notation.html) перелічує півребра проти годинникової стрілки від вхідного нижнього. Валідатор перевіряє кратність міток, планарну систему обертання й узгодженість напрямків.

Реалізований однокомпонентний [профіль DT](../v1/spec/dt-code.uk.md) містить `convention` і `code`; правила знаків та обходу прив’язані до [опису DT KnotInfo](https://knotinfo.org/descriptions/dt_notation.html). Конвенції інших пакетів не можна змішувати за самою формою масиву. Зокрема, [Spherogram](https://snappy.computop.org/spherogram.html) документує власні правила PD та нюанси відновлення орієнтації. Профіль перевіряє планарну реалізовність, але не відновлює єдиного PD-вкладення; масив `[4,6,2]` не оголошується універсальним безконтекстним форматом. Багатокомпонентний DT та вибір вкладення — окремі етапи.

## 3. Просторова крива

У HTML [сторінки 3_1](https://knotinfo.org/diagram_display.php?3_1) `point_array` містить 79 XYZ-точок. Початкова точка `[0.9008,-0.1947,0.0825]` не дублюється в кінці. Сторінка віднімає середнє координат, створює `THREE.CatmullRomCurve3` і встановлює `closed = true`. У [Three.js, який завантажує сама сторінка](https://knotinfo.org/Diagrams_All_Folders/diagrams_3d/three.js), типовий режим цієї кривої — `centripetal` (r132).

**Пропозиція адаптації:** `spatial-curve` має зберігати `points`, `closed` і точний варіант інтерполяції, наприклад `interpolation: {type: "catmull-rom", parameterization: "centripetal"}`. Для uniform і chordal потрібні інші явні значення. Не можна підміняти centripetal поточним uniform Catmull–Rom з `tension: 0.5` лише через спільну назву сімейства.

Вихідні координати без фізичних одиниць зберігаються як умовні. Віднімання середнього слід або залишити в операції кадрування, або явно записати як перетворення імпорту; не змінювати дані непомітно. Радіус трубки `0.02` і густина сітки на сайті є параметрами візуалізації, а не доведеним фізичним діаметром. Камера належить окремому `ViewDefinition`. Авторство геометрії на сторінці зазначено за Se-Goo Kim і Jaehyun Park.

## 4. Мозаїки: математична модель і справжні дані

Першоджерело: Lomonaco, Kauffman, [Quantum Knots and Mosaics](https://arxiv.org/abs/0805.0339), визначення 1 та рисунок набору плиток на сторінці 5 PDF. Мозаїка — квадратна матриця з 11 орієнтованих плиток; точки з’єднання сусідніх клітин мають збігатися. Для замкненого вузла немає виходів за зовнішню межу.

Авторський сайт [Aaron Heap — Knot Mosaics](https://www.geneseo.edu/knotmosaics) посилається на [репозиторій даних і програм](https://github.com/amheap/knot-mosaics). Перевірено редакцію `4d1c78ea5a1e8cf4783806f822c63e9bf3c1aaac`:

- [allKnots.csv](https://github.com/amheap/knot-mosaics/blob/4d1c78ea5a1e8cf4783806f822c63e9bf3c1aaac/websiteFunctions/flaskApp/allKnots.csv): колонки `OtherName,Name,Vector,Crossings,Mosaic,TileNum`.
- [mosaic_drawing.py](https://github.com/amheap/knot-mosaics/blob/4d1c78ea5a1e8cf4783806f822c63e9bf3c1aaac/pythonFiles/mosaic_drawing.py): значення 0–10 і розміщення матриці по рядках.
- [base_dt_make](https://github.com/amheap/knot-mosaics/blob/4d1c78ea5a1e8cf4783806f822c63e9bf3c1aaac/base_dt_make): словник шаблонів `layoutDict`. Для інших рядків CSV вектор може містити лише змінні клітини, тому його не можна завжди просто перетворювати на квадрат.

Для `3_1` CSV містить саме повний вектор із 16 значень. Його розкладення по рядках дає справжню матрицю:

```json
{
  "tileSet": "https://yuriyapostol.github.io/knot-engine/v1/tile-sets/lomonaco-kauffman-11",
  "tiles": [
    [0, 2, 1, 0],
    [2, 9, 10, 1],
    [3, 10, 8, 4],
    [0, 3, 4, 0]
  ]
}
```

`tileSet` і оболонка `tiles` — **наша запропонована JSON-серіалізація**, а не оригінальний формат CSV чи вже опубліковане визначення. Самі числа походять із таблиці. Це авторський приклад для того самого каталожного вузла; окремого доказу побайтової відповідності PNG KnotInfo немає.

Позначення N/E/S/W означають верх/праворуч/низ/ліворуч клітини; рядки йдуть зверху вниз. За рисунком статті та перевіреним кодом малювання:

| Код | З’єднання |
| --- | --- |
| 0 | Порожня клітина |
| 1 / 2 / 3 / 4 | W–S / S–E / N–E / N–W відповідно |
| 5 / 6 | W–E / N–S |
| 7 | W–S і N–E, без перетину |
| 8 | N–W і S–E, без перетину |
| 9 | W–E над N–S |
| 10 | N–S над W–E |

Контракт `mosaic-diagram.data`: обов’язкові `tileSet` і квадратна непорожня `tiles`; розмір виводиться з матриці, не дублюється. Набір плиток має власне визначення: допустимі коди, з’єднання портів, порядок проходження зверху та знизу, конвенція координат. Поточна пропозиція підтримує лише наведений набір; інший набір не можна прийняти за збігом цілих кодів.

Перевірки: прямокутність і квадратність, коди, узгодженість портів сусідів, закрита зовнішня межа; компоненти підраховуються обходом з’єднань. Матриця вище має 12 непорожніх плиток, три перехрестя та один замкнений компонент. Мінімальність не випливає зі структури: це окреме твердження з джерелом. Якщо один рисунок мінімізує розмір, а інший число плиток, обидва є `mosaic-diagram`, із різними характеристиками.

## 5. Сіткові діаграми: не нав’язувати X/O джерелу

KnotInfo має [опис сіткових діаграм](https://knotinfo.org/descriptions/grid_notation.html), [SVG 3_1](https://knotinfo.org/Diagrams_All_Folders/diagrams_grid/grid3_1.svg) і таке `grid_notation` у записі вузла:

```json
[[1,1],[1,3],[2,2],[2,4],[3,3],[3,5],[4,1],[4,4],[5,2],[5,5]]
```

Це десять кінцевих точок на сітці 5×5, по дві в кожному рядку/стовпці, а не готові масиви X/O. За конвенцією KnotInfo вертикальні відрізки проходять над горизонтальними. Координати SVG відповідають цим парам із другою віссю вниз. При перенесенні в математичну систему з віссю вгору потрібне явне перетворення: не можна віддзеркалити дані мовчки.

Реалізовано один тип `grid-diagram` із кодуваннями `xo` та `vertex-pairs`, обидва з індексацією від 0 і фіксованими осями та перетинами. Джерельні конвенції адаптуються під час імпорту. X/O задає орієнтацію; `vertex-pairs` її не задає. Точні контракти — у [специфікації сіткових діаграм](../v1/spec/grid-diagram.uk.md).

## 6. Рекомендований порядок

1. `diagram-image` для точного збереження доступних рисунків і `planar-diagram` для редагованої плоскої геометрії з явними перехрестями. Перший не підміняє другий.
2. `pd-code` як компактна комбінаторна діаграма без залежності від layout. Окремий засіб візуалізації може будувати layout, не записуючи результат алгоритму як оригінальне зображення.
3. `spatial-curve` із точними правилами замикання та параметризації; це прямо покриває 3D-дані дослідженої сторінки.
4. `mosaic-diagram`: є і математичне визначення, і реальні структурні дані для перевірки імпорту.
5. Обидва кодування сіткових діаграм та однокомпонентний числовий DT реалізовано; багатокомпонентний DT та інші нотації потребують окремих контрактів і перевірки конвенцій.

Такий порядок — пропозиція, а не припущення про пріоритети всіх користувачів. Для практичних вузлів найкориснішими можуть бути просторова геометрія та ілюстровані процедури; для дослідників — комбінаторні коди й мозаїки. Жоден із цих випадків не потребує окремої кореневої колекції `diagrams`.

До реалізації кожного імпорту потрібні приклади з першоджерел та перевірки того, що зберігається: координати, замикання, компоненти, перехрестя, орієнтація й джерело перетворення. Автоматична математична тотожність різних представлень залишається окремою задачею.
