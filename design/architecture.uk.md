# Архітектура knot-engine

Початковий профіль перегляду `KnotAsset` реалізовано. Авторитетні поточні контракти: [дані](../v1/specifications/knot-asset.uk.md), [функції](../v1/specifications/functions.uk.md), [компонент](../v1/specifications/components.uk.md). [Ширший проєкт](knot-asset-draft.uk.md) ще містить майбутні роботи; це не означає, що всі запропоновані поля вже приймаються.

```text
KnotAsset / самостійні дані / явно передані реєстри
  → структурна перевірка з обмеженням ресурсів
  → розгортання URI, перевірка посилань і доменної семантики
  → звіт повноти
  → вибір представлення й ракурсу
  → RenderableModel
  → побудова геометрії + підготовка камери
  → KnotViewer / знімок PNG
```

Core не містить Vue, Three.js, доступу до браузера або мережевого resolver. Контракти JSON Schema мають спільне джерело `src/core/contracts.json`; незалежні опубліковані схеми генеруються через `npm run build:schemas`. Семантична валідація окремо перевіряє зв’язки між записами й геометричні/комбінаторні правила.

Компонент `KnotViewer` приймає об’єкт `KnotAsset`, вибір представлення та необов’язковий контекст реєстрів/ракурсу. Старий model-вхід, адаптери, схеми й тести сумісності видалено. Спільні помилки й типи рендерингу більше не належать legacy-модулю. Геометрія підтримує polyline та явні uniform/centripetal/chordal Catmull–Rom. Перспективна й ортографічна камери використовують спільну підготовку для екрана та знімків.

Демка сайту використовує лише публічний API. Редагується весь об’єкт `KnotAsset`, зберігається вибір представлення, якщо воно ще існує, а при некоректному редагуванні залишається останній коректний об’єкт `KnotAsset`. Іменовані стани належать конструкціям; кожне статичне представлення позначає свій стан. Процедури вибирають представлення без вимог відповідності для інтерполяції.

Виділення включає потрібні конструкції й ресурси. Композиція обмежена фрагментами одного документа; об’єднання незалежних авторів не виводиться неявно. Дані невідомого типу структурно читаються, але не отримують повного семантичного звіту. Додаткові формати, твердження й анімація потребують власних контрактів і тестів.

Перевірки: типізація, модульні/схемні тести, збірки бібліотеки/демки, браузерні тести, споживач tarball і тести сайту/посилань. Реальні touch, WebView та фізична коректність вузлів цими перевірками не встановлюються. Версії залишаються 0.1.0 для пакета та `schemaVersion` 1.

CSS використовує простір імен пакета `knot-engine`, за яким ідуть мажорне покоління та назва компонента: `.knot-engine-v1-viewer…` і `--knot-engine-v1-viewer-*` для `KnotViewer`. Інші компоненти отримують власні назви в тому самому просторі пакета/покоління. Різні мажорні версії можна використовувати на одній сторінці. На початковій стадії зворотна сумісність CSS, як і решти пакета, не вимагається. Деталі — у [політиці публікації](publication.uk.md#простір-імен-css-для-мажорних-поколінь) та [контракті компонента](../v1/specifications/components.uk.md#простір-імен-css-та-оформлення).

## Запланована композиція переглядачів і окремі параметри перегляду

Це погоджений напрям майбутньої реалізації. Поточні контракти даних і компонента, на які наведено посилання вище, поки описують реалізовану поведінку.

Для різних типів представлень потрібно розробити окремі компоненти переглядачів. Головний `KnotViewer` вибиратиме відповідний компонент за розгорнутим URI типу представлення й делегуватиме йому відображення. Окремі переглядачі також мають бути придатні для самостійного використання. Додавання переглядача представлення не повинно вимагати внесення його логіки відображення в головний компонент. Саме визначення типу не встановлює переглядач; для непідтримуваного типу потрібна явна діагностика.

Переглядачі повинні мати узгоджений API для даних представлення й потрібного доменного контексту, окремо переданих параметрів перегляду, доступних підписів, мови/теми, подій життєвого циклу й помилок та застосовних методів на кшталт скидання, вписування й знімка. Спільна поведінка та значення помилок мають бути узгоджені. Специфічні для типу параметри й можливості потрібно оголошувати явно: текстовий або площинний переглядач не зобов’язаний підтримувати 3D-камеру. Головний компонент передає параметри, виклики методів і події через цей спільний контракт.

Параметри відображення потрібно відділити від даних вузла й доменних даних. Застосунок передаватиме їх окремим входом переглядача замість вкладення в `KnotAsset` або дані представлення. Сюди належать положення й орієнтація камери, проєкція, кадрування, масштабування/панорамування, візуальне оформлення та параметри взаємодії. Треба переглянути наявні `Representation.views`, `defaultView` і `preferredView` та перенести їхню роль налаштувань відображення до окремого контракту. Іменовані набори параметрів можна зберігати незалежно й пов’язувати з ID представлення; формат зберігання й точний API ще потрібно спроєктувати. Зміна камери, вибір набору параметрів або взаємодія з переглядачем не повинні змінювати дані вузла. Відображення на екрані та знімки мають узгоджено використовувати окремо передані параметри.

Системи координат, одиниці вимірювання, авторська геометрія, топологія, математичні конвенції та змістові стани конструкцій залишаються доменними даними. Орієнтація камери є параметром перегляду; конвенція орієнтації, яка визначає зміст координат або діаграми, є доменними даними. Файли вузлів мають залишатися валідними й корисними без збережених параметрів перегляду; за їх відсутності переглядачі застосовують документовані типові значення.

До завершення реалізації потрібно визначити спільні контракти переглядачів і параметрів, перенести наявний просторовий переглядач за головний компонент, додати відповідні переглядачі підтримуваних типів, оновити схеми/приклади та описати відокремлення від поточних вкладених полів ракурсів. Критерії приймання мають охоплювати самостійне й делеговане використання, перемикання типів, непідтримувані можливості, незалежні параметри двох переглядачів тих самих даних, узгодженість знімків і незмінність вхідних даних.
