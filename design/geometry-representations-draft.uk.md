# Проєкт контрактів геометрії 2D/3D і станів процедури

> Статус: проєкт для узгодження, **не чинна специфікація v1**. Код, JSON Schema та переглядачі поки не змінено.

## Мета та сумісність

Запропоновані URI типів представлень закінчуються на `representation-types/2d` та `representation-types/3d`. У JSON прикладах нижче для читабельності показані короткі назви; фактичне поле `Representation.type` використовує URI, як і зараз. Наявний `spatial-curve` поки залишається чинним. Його міграцію слід визначити окремо перед реалізацією. `grid-diagram`, `mosaic-diagram`, `pd-code`, `dt-code` не замінюються цими типами.

`Representation` і `target` залишаються наявними. `Construction.objects`, `Construction.states` та `target.kind: "state"` **залишаються**. `Procedure.steps[].representations` також зберігається.

## Геометричні дані

Обидва типи мають `data.elements` — непорожній масив різнорідних геометричних елементів із локально унікальними `id`. Кожен елемент має `type` та необов'язковий `object` — локальний ID предмета цільової конструкції. Відсутність `object` дозволяє зображувати сам предмет опису. Координати всіх елементів задані в **єдиній системі координат представлення**; локальні трансформації, інстанси та повторне використання геометрії поки не вводяться.

Початкові примітиви: `curve` у 2D та 3D, `mesh` лише у 3D. `curve` зберігає `closed`, `interpolation`, `points` і чинну семантику кривих. 2D-точка — пара чисел, 3D-точка — трійка. `mesh` має `vertices` (3D-точки) та `faces` (трійки індексів вершин із нуля). Сітка описує поверхню, а не обов'язково замкнене фізичне тіло.

Для `3d` початково зберігається нинішній `coordinateSystem` із `spatial-curve`: `handedness: "right"`, `upAxis: "y"`, `scale: {kind:"relative"}` або `{kind:"physical",metersPerUnit: ...}`. Точний 2D-контракт `coordinateSystem` (осі, орієнтація, масштаб) треба визначити перед реалізацією.

### Приклад 3D

```json
{
  "id": "final-3d",
  "type": "3d",
  "data": {
    "coordinateSystem": {
      "handedness": "right",
      "upAxis": "y",
      "scale": { "kind": "relative" }
    },
    "elements": [
      {
        "id": "rope-path",
        "type": "curve",
        "object": "rope-1",
        "closed": false,
        "interpolation": { "type": "polyline" },
        "points": [[0, 0, 0], [1, 1, 0], [2, 0, 0]]
      },
      {
        "id": "support-surface",
        "type": "mesh",
        "object": "support-1",
        "vertices": [[0, 0, -1], [2, 0, -1], [2, 1, -1]],
        "faces": [[0, 1, 2]]
      }
    ]
  }
}
```

## Перетини у 2D

`data.crossings` — необов'язковий впорядкований масив проходжень через звичайні поперечні геометричні перетини кривих. Кожен фізичний перетин має **рівно два записи** з однаковим `id`. Запис містить `element` (крива поточного проходження) та **рівно одне** з полів `underElement` (інша крива проходить під поточною) або `overElement` (інша крива проходить над поточною). Два записи з однаковим `id` мають бути взаємно узгоджені; самоперетин має два входження однієї кривої, одне верхнє, друге нижнє.

Для кожного `element` підпослідовність записів у загальному масиві задає порядок проходження геометричних перетинів від початку кривої. Для замкненої кривої початок визначається першою контрольної точкою. Координати, параметри сегментів та частки довжини в `crossings` не зберігаються. Переглядач обчислює геометричні перетини та зіставляє їх за порядком уздовж обох кривих і спільними ID. Не можна довільно зіставляти неоднозначні дані.

```json
{
  "crossings": [
    { "id": "x1", "element": "rope-a", "underElement": "rope-b" },
    { "id": "x2", "element": "rope-a", "overElement": "rope-b" },
    { "id": "x2", "element": "rope-b", "underElement": "rope-a" },
    { "id": "x1", "element": "rope-b", "overElement": "rope-a" }
  ]
}
```

Самоперетин:

```json
{
  "crossings": [
    { "id": "x1", "element": "rope-a", "underElement": "rope-a" },
    { "id": "x1", "element": "rope-a", "overElement": "rope-a" }
  ]
}
```

Потрібно формально перевірити геометричне зіставлення для кількох перетинів тих самих кривих, самоперетинів, замкнених кривих та інтерполяції Catmull–Rom. Дотики, збіжні ділянки та неоднозначні перетини не входять до початкового профілю. Потрібно визначити числові допуски й реакцію валідатора/переглядача на невідповідність геометрії.

## Проміжні стани процедури

Повні `Representation` призначені для самодостатніх станів (насамперед фінальних). Процедура може посилатися на **базове представлення**, а кроки — містити **локальні перевизначення** геометрії. Кожен крок обчислюється **незалежно від інших кроків**, застосуванням змін до тієї самої бази; послідовних патчів немає. Базою може бути фінальний стан. Крок без перевизначень може посилатися на базу/інші представлення через наявний механізм.

Погоджена семантика операцій: `replace` замінює **весь** елемент за ID, `add` додає повний елемент із новим ID, `remove` вилучає елемент за ID лише з результату конкретного кроку. Для 2D крок має мати можливість повністю перевизначити список `crossings` (зокрема порожнім масивом), адже геометрія перетинів змінюється. Незмінені елементи успадковуються з бази.

Назви та вкладеність полів визначено в розділі «Нормативний контракт перевизначень кроків». Крок не змінює тип або систему координат бази; для іншого типу потрібне окреме представлення.

Проміжні фази анімації між кроками, матеріальні координати вздовж мотузки, локальні трансформації, повторне використання геометрії та часткові патчі окремих координат **відкладені**.

## Нормативний контракт перевизначень кроків

У `Procedure` додається необов'язкове поле `base: Reference`, яке посилається на повне геометричне представлення `2d` або `3d`. У `Step` додається необов'язкове поле `data`:

```json
{
  "base": { "id": "final-3d" },
  "steps": [
    {
      "id": "step-1",
      "data": {
        "remove": [],
        "replace": [
          {
            "id": "rope-path",
            "type": "curve",
            "closed": false,
            "interpolation": { "type": "polyline" },
            "points": [[0, 0, 0], [1, 0, 0], [2, 0, 0]]
          }
        ],
        "add": []
      }
    },
    { "id": "step-final" }
  ]
}
```

Це фрагмент процедури; точний синтаксис `Reference` визначається наявним контрактом посилань. Кожне `Step.data` незалежно застосовується до `Procedure.base`. `remove` містить ID елементів, `replace` — повні елементи з наявними ID, `add` — повні елементи з новими ID. ID в операціях не можуть конфліктувати. Відсутні операції означають порожні списки. Результат зберігає тип і систему координат бази.

Для бази `2d` поле `Step.data.crossings` необов'язкове і, якщо присутнє, **повністю замінює** `base.data.crossings`; порожній масив скасовує всі перетини. Якщо `crossings` відсутнє, список успадковується. Результат кроку має бути геометрично узгодженим, тому після зміни кривих потрібно перевіряти успадковані перетини. Для `3d` поле `crossings` заборонене.

Якщо `Step.data` присутнє, `Procedure.base` обов'язкове. Крок без `data` не змінює базу. Чинне `Step.representations` залишається незалежним способом додати ілюстрації. Для іншого типу представлення використовується окреме повне представлення.

## Перед реалізацією

1. Втілити точні TypeScript-типи, JSON Schema, 2D-систему координат і межі числових значень.
2. Перевірити відповідність порядкових записів перетинів реальній геометрії, зокрема для самоперетинів.
3. Реалізувати `Procedure.base` і `Step.data` з операціями `replace/add/remove` та `crossings`.
4. Визначити міграцію `spatial-curve`, збереження чинних даних, вплив на валідатори, переглядачі, приклади й документацію.
