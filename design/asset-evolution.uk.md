# Розвиток `KnotAsset`

**Історична пропозиція, замінена [поточним переглядом](knot-asset-draft.uk.md).** Запропоновані нижче окремі diagrams/notations не є погодженою цільовою архітектурою.

Поточний формат добре розділяє фізичні елементи, геометричні стани, алгоритми зав’язування та налаштування камери. Його головне обмеження — координатне представлення є єдиним способом описати вузол. Сіткова діаграма не потребує сплайнів, фізичного діаметра або метражу. Тому додано окремий `GridDiagram`, який можна передавати компоненту без повного об’єкта `KnotAsset`, і можливість отримати зменшений самодостатній `KnotAsset`.

[KnotInfo для 3_1](https://knotinfo.org/diagram_display.php?3_1) показує KnotScape, SnapPy, 3D, сіткові та мозаїчні діаграми, зокрема дзеркальні діаграми. [Основна таблиця](https://knotinfo.org/) містить Gauss, DT, PD, Conway та braid нотації, матриці Seifert, числові й поліноміальні інваріанти та інші характеристики. Це різні види даних із різними правилами перевірки, а не різновиди координатних точок.

Рекомендований подальший розвиток:

- `diagrams`: дискримінований союз grid, mosaic та інших комбінаторних діаграм. Для mosaic потрібні окремі правила орієнтації, набору tiles і сумісності сусідніх країв.
- `notations`: типізовані Gauss, DT, PD, Conway, braid записи. Кожен тип має явно визначати орієнтацію, знак перехрещень, індексацію та компонентність. Не слід зберігати їх як неоднозначний рядок без конвенції.
- `mathematicalPresentations`: групові презентації, матриці Seifert та інші структуровані математичні дані. Назва має відрізнятися від наявного `presentation`, що означає камеру та стиль.
- `invariants`: типізовані значення з позначенням exact, bound, interval або unknown. Для поліномів потрібні змінні, нормалізація та точні коефіцієнти; великі цілі й раціональні числа не варто зберігати як неточний JavaScript number.
- `sources`: бібліографія, походження, ліцензія, дата отримання та посилання записів на джерела. Зовнішні адреси мають бути даними, а не автоматично завантажуваними ресурсами.
- `relations`: явно типізовані mirror, reverse та інші зв’язки між ідентичностями. Дзеркало не слід прирівнювати до декоративного `Variant` без визначення математичної еквівалентності.

Ці розділи поки не реалізовані: довільний `metadata: Record<string, unknown>` приховав би різницю між відсутнім, невідомим і доведеним значенням. Нові записи варто додавати з власними типами, підсхемами, конвенціями та перевірками, коли буде конкретний приклад даних.

`schema` ідентифікує вид документа, `schemaVersion` — його контракт, `$schema` — адресу JSON Schema для редакторів. У вкладених значеннях назва схеми не дублюється; їхній тип задається полем `type` або контекстом. Підсхеми зараз доступні як окремі schema entry points зі спільними `$defs`, щоб не дублювати правила. Для незалежного версіонування майбутніх нотацій можна винести визначення в окремі файли й додати envelope із назвою та версією саме цього контракту.

`composeKnotAsset` об’єднує самодостатні фрагменти одного вузла, перевіряє конфлікти ID та фінальний результат. `selectKnotAsset` виділяє потрібні види даних разом із залежностями. Це збірка даних у пам’яті; механізми manifest, зовнішнього зберігання та завантаження не є частиною доменної моделі.

`validateGridDiagram` уже перевіряє окрему сіткову діаграму без повного об’єкта `KnotAsset`. Наявний 3D засіб візуалізації продовжує працювати тільки з координатними представленнями. Наступним практичним кроком може бути компонент перегляду сіткових діаграм з входом `GridDiagram`; загальний компонент перегляду не повинен змушувати кожен спеціалізований компонент знати всі розділи `KnotAsset`.
