# Архітектура та міграція knot-engine

[English](architecture.md) | [Українська](architecture.uk.md) · [Документація](../README.uk.md)

[**KnotAsset v1**](knot-asset-v1.uk.md) є авторитетною специфікацією доменних даних. [KnotModelV1](model-format.uk.md) залишається окремим legacy-форматом статичної геометрії для рендерингу. Їхні значення `schemaVersion: 1` належать різним контрактам. Ні validator, ні viewer не визначають формат за цим числом.

```text
KnotAsset → validateKnotAsset → resolveKnotAsset (3D representation + snapshot) ─┐
                                                                          ├→ RenderableModel → geometry builder → renderer
KnotModelV1 → validateKnotModelV1 → resolveKnotModelV1 ────────────────────────┘                                  ├→ KnotViewer
                                                                                                              └→ capture/preview
Майбутній редактор → створює дані KnotAsset, а не сцену Three.js у renderer
```

Типи, validators і resolvers у core не залежать від Vue, Three.js, браузера чи завантаження файлів. `RenderableModel` містить скопійовані криві, необов'язкову підготовлену камеру й попередження; це внутрішня структура рендерингу, а не ще один версійований авторський формат. Geometry builder приймає лише цю структуру. Renderer відповідає за керування камерою, життєвий цикл сцени й захоплення зображень та ніколи не обходить representations або algorithms.

Назва Vue-компонента `KnotViewer` зберігається разом із його CSS-класами й токенами `--knot-viewer-*`. Назва npm-пакета та проєкту — `knot-engine`. Legacy JSON Schema зберігає історичний `$id`, щоб наявні посилання на схему залишалися чинними; нова схема має окремі ім'я файла `knot-asset-v1.schema.json` та ID. Обидві схеми експортуються пакетом.

## Доповнення до API

- `validateKnotAsset(value, { strict? })` повертає `{ valid: true, asset, warnings }` або `{ valid: false, issues }`.
- `validateKnotModelV1(value, { strict? })` — явний legacy API. Наявний `validateModel` і формат його результату збережені як псевдонім.
- `resolveKnotAsset(value, { representationId?, snapshotId? })` перевіряє **весь** asset, вибирає 3D snapshot і повертає дані рендерингу. Невалідні snapshots, які не вибрано, також спричиняють помилку валідації.
- `resolveKnotModelV1(value)` перевіряє й адаптує legacy-моделі, зберігаючи радіуси та камери preview.
- Наявний API `KnotViewer :model="legacyModel"` підтримується. `:asset="asset"`, `representation-id` і `snapshot-id` додають окрему доменну точку входу. Якщо обидва входи не null, повертається `INVALID_MODEL`; відсутність обох означає наявний порожній стан.

Без ID вибору resolver використовує перше представлення з `dimension: 3`, а потім його перший snapshot. Явні ID мають існувати у відповідній області. Вибір ніколи не інтерпретує написання ID. Вибір 2D повертає `UNSUPPORTED_SCHEMA`; порожнє представлення або snapshot неможливо відрендерити. Порожні доменні колекції є валідними даними, як у прикладі кореневої структури специфікації.

Заміна asset або зміна вибору перебудовує viewer; глибока зміна об'єкта на місці не підтримується. Анімація кроків не відбувається. `ready`, `error`, `camera-change`, slots і методи захоплення зберігають legacy-форми; для входу asset поле `ready.modelId` містить ID asset. Валідація та вибір завершуються до створення WebGL або виділення пам'яті під геометрію.

`AssetCameraView` — назва доменного типу камери з необов'язковим `fov`. Наявний тип viewer `CameraView` зберігає обов'язковий `fov`, щоб не порушувати сумісність зі споживачами. Якщо доменний FOV пропущено, resolver задає 55°. Камера представлення спільна для всіх його snapshots. `initialCamera` залишається перевизначенням для viewer; захоплення `model-preview` використовує підготовлену камеру представлення.

## Явні політики реалізації та неоднозначності специфікації

Доменний документ вимагає допустиму tension, мінімальну кількість точок та окремі ресурсні ліміти, але не задає чисел. Ця реалізація використовує наведену нижче явну політику, відображену в новій схемі й тестах, замість успадкування лімітів legacy validator:

- Tension Catmull–Rom є скінченним числом у межах `[0, 1]`. Відкриті криві потребують щонайменше 2 точок, замкнені — щонайменше 3.
- Точки повинні мати рівно стільки координат, скільки задає розмірність представлення, і всі координати мають бути скінченними. Послідовні дублікати й повторні кінцеві точки замкненої кривої перевіряються через **точну рівність координат**. Legacy epsilon, залежний від масштабу, і межі координат не застосовуються до доменної валідації.
- ID та посилання є непорожніми рядками без legacy-ліміту довжини ID. ID елементів, представлень, алгоритмів і варіантів унікальні у своїх кореневих колекціях. ID snapshots унікальні в межах представлення, ID елементів snapshot — у межах snapshot, ID кроків — у межах алгоритму, а RopeEnd ID — у межах мотузки. Різні мотузки можуть повторно використовувати ID кінців, наприклад `a` і `b`. Специфікація явно не задає область RopeEnd; це рішення випливає з їхньої належності мотузці та відсутності глобальних посилань на кінці.
- Необов'язкові фізичні довжина й діаметр мають бути додатними скінченними значеннями в метрах. Геометрична довжина не порівнюється з фізичною, а геометричне замикання — з топологією мотузки.
- Перехрещення посилаються на елементи, присутні у власному snapshot, оскільки описують відношення геометрії в цьому стані. Специфікація не вимагає певного фізичного типу цих елементів. Необов'язковий ID перехрещення не використовується як ціль посилання й не має додаткового правила унікальності.
- Вектори камери містять три скінченні координати, position відрізняється від target, а необов'язковий перспективний FOV лежить у межах `(0, 180)` градусів. Документ описує лише поведінку 3D-камери; дані камери можна зберігати у 2D-представленні, але семантика 2D-камери або рендерингу не вигадується.
- Послідовні кроки алгоритму порівнюють кількість точок кривих елементів, присутніх в обох snapshots. Елементи, відсутні в одному зі станів, не утворюють пару для анімації. Стабільний порядок точок і значення/напрямок `u` є обов'язками автора; числова валідація не може їх довести.
- Runtime за замовчуванням приймає невідомі поля для узгодженості з legacy API. `{ strict: true }` відхиляє невідомі поля на кожному визначеному рівні об'єктів, відповідно до закритої JSON Schema. Невідомі типи елементів, геометрії, інтерполяції та версії схеми завжди відхиляються.

`KNOT_ASSET_LIMITS` визначає ресурсний профіль:

| Колекція/бюджет | Максимум |
| --- | ---: |
| Елементи | 256 |
| Представлення | 32 |
| Snapshots на представлення | 256 |
| Елементи на snapshot | 256 |
| Алгоритми | 256 |
| Кроки на алгоритм | 1024 |
| Варіанти | 1024 |
| Перехрещення на snapshot | 4096 |
| Точки на криву | 4096 |
| Точки в усіх snapshots | 65536 |
| Загальна кількість записів у всіх масивах, які обходить validator | 262144 |

Останній бюджет рахує записи в масивах доменних колекцій, кінців і точок, а не окремі компоненти координат. Завеликі масиви відхиляються до їхнього обходу. Сукупні бюджети, унікальність ID, цілісність посилань, повторні точки, відмінність позиції камери від цілі та відповідність станів алгоритму — це **семантичні перевірки runtime**; самої JSON Schema недостатньо. Структурні тести схеми охоплюють обидві розмірності й усі валідні fixtures та відокремлюють суто семантичні помилки.

## Політика першого рендерингу

Кожна вибрана крива використовує наявний конвеєр побудови трубок. Для мотузки із заданим діаметром радіус дорівнює `diameter / 2`. За відсутності діаметра або для кривої опори/карабіна renderer використовує **радіус відображення 0.005 м і видає попередження**. Це не вигадує фізичних розмірів чи стандартизованої конструкції опори/карабіна. Відображається лише авторська геометрія кривої. Фізична топологія не змінює торці або замикання: вони визначаються `geometry.closed`.

Домен не стандартизує зовнішній вигляд або реєстр пресетів. Перший renderer використовує наявне оформлення; непідтримуваний presentation preset спричиняє попередження. Політика renderer окремо відхиляє координати/компоненти камери поза межами ±1,000,000 м і радіуси поза `(0, 1,000,000]` м до виділення пам'яті під геометрію. Це ліміти renderer, а не обмеження координат KnotAsset. Наявні профілі деталізації й бюджет 100,000 трикутників зберігаються: якість зменшується до виділення пам'яті, або повертається `LIMIT_EXCEEDED`, якщо навіть низька якість не вкладається в бюджет. Legacy-дані зберігають власні ліміти валідації.

## Приклади та перевірка

`examples/models/` зберігається без змін для legacy-регресійних тестів. `examples/assets/` містить нейтральні технічні fixtures для відкритої/замкненої мотузки, двох мотузок, опори, карабіна, кількох snapshots, алгоритмів зі спільним фінальним станом, варіантів і 2D-перехрещень. Ці криві не заявлені як перевірені практичні вузли. `examples/assets/invalid/` містить некоректні приклади; тести додатково перевіряють значення поза JSON, як-от NaN/Infinity, області посилань, заморожені вхідні дані та ресурсні межі.

Виконайте `npm run typecheck`, `npm test`, `npm run build`, `npm run build:demo`, `npm run test:browser` і `npm run test:package`. Браузерний скрипт потребує локального Chrome або `CHROME_PATH`; він перевіряє справжній WebGL із програмним рендерингом, обидва legacy fixtures, заміну snapshot asset, захоплення зображень, відхилення до створення WebGL і вибір у демо. Тест пакета розпаковує справжній npm tarball в ізольований проєкт-споживач; лише залежності Vue/Three/типів підключаються з робочого каталогу. Він перевіряє імпорти лише core, SSR, публічні декларації та клієнтську збірку включно з CSS. Це не чисте встановлення залежностей із мережі й не матриця мінімальних peer-версій.

У репозиторії немає скриптів форматування або lint. Наявний CLI `preview:model` залишається інтерфейсом для legacy-файлів; обидва Vue-входи використовують спільне захоплення зображень. Реальні сенсорні пристрої/WebView та піксельна еквівалентність між пристроями залишаються поза цими автоматизованими перевірками.

## Відкладені можливості

Модель і validator підтримують 2D; ця міграція рендерить лише статичні 3D snapshots. Анімація, графічний редактор вузлів, переходи, траєкторії, фізика, зіткнення, з'єднання, автоматична перевірка правильності вузла та mesh/primitive geometry не реалізовані. Майбутній редактор використовуватиме KnotAsset як джерело істини. Публікація, надсилання комітів і перейменування репозиторію є окремими операціями.
